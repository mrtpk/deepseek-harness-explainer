Life of a headless task

IntermediateGuided tourabout 9 min read + 1 min deep dives

Code version: DeepSeek Harness @ ce7073d · 2026-10-30

Before you read

This page uses ideas from these pages:

  • Everything is a plugin: Cordis Beginner
  • The agent loop and the session log Intermediate

In one sentence

This tour follows dsh --profile headless "task" from the command line to the answer that the runner prints on stdout. The answer is the last assistant text of the Agent.

The idea#

The headless bundle has no server and no browser: one task goes in, and one answer comes out (packages/bundle/headless/cordis.patch.yml:1-7). It still uses the same core pieces as every other surface: a profile, a plugin tree, an Agent, and the session log. This tour has nine stops, in three stages: starting the run, running the task, and finishing the run.

The picture#

Read each panel left to right; the three panels run top to bottom in call order. The number on each card matches the stop number below.

1bin.ts and args.ts parse the command line#

Node starts apps/cli/src/bin.ts. Its runCli() function calls parseDshArgs() with the raw argv (apps/cli/src/bin.ts:29). The Commander parser reads only the launcher's own flags. The first token that it does not recognize starts the inner arguments, and a variadic [args...] positional captures them (apps/cli/src/args.ts:4-9, apps/cli/src/args.ts:159-167). For dsh --profile headless "task", that leftover is ["task"]: it becomes part of the resolved ProfileInvocation (apps/cli/src/args.ts:117).

Line 35 starts runProfile(). Line 40 passes invocation.args (the ["task"] leftover) straight through.

2profile-boot.ts composes and boots the profile#

composeProfile() loads the named profile and reads any --patch overlays (apps/cli/src/profile-boot.ts:224-236). The bundle layers and patch files of a profile stack in a fixed order (apps/cli/src/profile-boot.ts:211-217, docs/architecture.md:25). runProfile() then calls the shared boot() helper with that patch stack (apps/cli/src/profile-boot.ts:323). boot() makes one Cordis context and mounts the plugin tree into it (packages/boot/app-boot/src/index.ts:1208, packages/boot/app-boot/src/index.ts:1228).

provideCmdline() turns the ["task"] leftover into the cmdlineArgs service (packages/boot/cmdline/src/index.ts:84-88). This call runs in the prepare callback of boot(), before the first config-tree entry mounts (packages/boot/app-boot/src/index.ts:1226-1228).

3The headless bundle mounts its two plugins#

The patch of the dsh-headless bundle inserts two rows (packages/bundle/headless/cordis.patch.yml:14-26). headless-startup injects cmdlineArgs and parses the task positional (packages/bundle/headless/src/startup.ts:21). headless-runner injects headlessStartup and reads its config values from that service (packages/bundle/headless/cordis.patch.yml:19-25).

The apply() function of headless-startup joins the positional words with spaces into one task string (packages/bundle/headless/src/startup.ts:121-125). Then it provides the parsed values as ctx.headlessStartup (packages/bundle/headless/src/startup.ts:148-155).

4AgentRegistry creates the Agent#

The run() function of headless-runner reads the core agents service (packages/bundle/headless/src/index.ts:326). When the command line has no --session-id, it calls agents.create() with a new random session id (packages/bundle/headless/src/index.ts:385, packages/bundle/headless/src/index.ts:388-394).

AgentRegistry.create() looks up the registered factory and calls its createAgent() (packages/core/agent/src/index.ts:416-426). The agent loop and the session log explains what that factory builds.

5The task is submitted with agent.followup()#

The runner first waits one time for the new Agent to become idle (packages/bundle/headless/src/index.ts:396). Then it puts the task text into a user message and calls agent.followup() (packages/bundle/headless/src/index.ts:420-423).

followup() queues the message for the next turn and wakes the Agent's driver (packages/core/agent-loop/src/agent.ts:179-181).

6The turn/step loop drives the model#

When the driver wakes, it starts kick() (packages/core/agent-loop/src/agent.ts:250). kick() calls the private turn() method in a loop while turn() returns true (packages/core/agent-loop/src/agent.ts:268-270). Each turn() call opens one turn and runs zero or more steps against the model (packages/core/agent-loop/src/agent.ts:336, packages/core/agent-loop/src/agent.ts:356-358). This tour does not repeat that loop: The agent loop and the session log covers the turn/step mechanism and the session log in detail.

7Tool calls run through the tool pipeline#

When a step's model response includes tool calls, the loop hands them to the tool service in one batch (packages/core/agent-loop/src/agent.ts:590-593).

A call that passes each stage runs through three waterfalls, in this order: tools/pre-execute, tools/execute, tools/post-execute (packages/core/tools/src/pipeline.ts:199-201, packages/core/tools/src/pipeline.ts:299-301, packages/core/tools/src/pipeline.ts:487-489). Tools and MCP servers is the page for this pipeline.

8The runner waits for idle, and for any subagents#

After the runner submits the task, it runs a loop. The loop waits for the Agent to become idle. Then it asks whether child subagents still have work in progress (packages/bundle/headless/src/index.ts:424-431).

waitForChildren() waits for child work in progress. It returns true when it waited, and then the runner must check the parent again (packages/subagent/subagent/src/manager.ts:247-252).

9The session flushes, and the result reaches stdout#

When the wait loop ends, the runner calls sessions.flush() (packages/bundle/headless/src/index.ts:435). SessionStore.flush() sends the buffered events of the session to durable storage (packages/core/session/src/index.ts:1329-1346).

Line 437 reads the log again from the first sequence number of the task (packages/bundle/headless/src/index.ts:407). It keeps the last non-empty assistant text of the interval, and the end reason of the last turn (packages/bundle/headless/src/index.ts:84-111). Line 438 writes that text to stdout. Line 443 requests exit code 0 only when the reason kind is completed, and 1 in all other cases.

More detail#

This tour follows the plain-text path: no --json, no --session-id. With --json, a projection object writes the run to stdout as newline-delimited events instead of the final text (packages/bundle/headless/src/index.ts:408, packages/bundle/headless/src/startup.ts:58). With --session-id, stop 4 changes: the runner adopts an existing Session and does not make a new one (packages/bundle/headless/src/index.ts:395). It rejects an id that does not exist, or that is live in this process (packages/bundle/headless/src/index.ts:277-287, packages/bundle/headless/src/index.ts:297-303). It also rejects a session that records an agent preset, a subagent session, and a session from a different working directory (packages/bundle/headless/src/index.ts:222-242).

Other flags change the run before the task starts. --permission-mode selects a configured permission preset. --approval-policy sets the approval behavior after that preset (packages/bundle/headless/src/index.ts:339-349). The runner applies both to the session before agent.followup() at stop 5 (packages/bundle/headless/src/index.ts:403-406). --add-dir adds write roots, and the runner checks that the sandbox-policy row includes them (packages/bundle/headless/src/index.ts:350-356).

For the generated sequence diagram of one turn, and the tool pipeline's full event reference, see the repository's own docs/agent-lifecycle.md and docs/tool-execution-pipeline.md.

Deep dive

Exactly when does the wait loop at stop 8 stop?

The loop at packages/bundle/headless/src/index.ts:424-431 does not stop as soon as the Agent looks idle. It stops only when all four of these conditions are true at the same time:

  1. The whenIdle() of the Agent has resolved for this pass of the loop.
  2. subagents.waitForChildren(agent) returns false: it did not wait for child work. When no subagents service is mounted, this check also passes.
  3. The status of the Agent is still idle.
  4. The sequence number of the session has not increased since whenIdle() resolved (agent.session.seq === idleSeq).

The last two checks are for one race. The code comment says that a child can settle and wake the parent before the child wait observes it (packages/bundle/headless/src/index.ts:428). The status check and the sequence check find new parent work that started in that gap (packages/bundle/headless/src/index.ts:429-430). Without them, the runner can flush and print before the new parent turn ends.

What can go wrong#

A later turn can clear an agent/error

Do not call a run failed only because an agent/error event occurred. Look at the last turn/end event too. The runner records an agent/error of its Agent as a failure. A later turn/end of the same session, at or after the log offset of that error, clears the failure (packages/bundle/headless/src/index.ts:411-417). The runner throws a failure that remains after the flush (packages/bundle/headless/src/index.ts:436).

A flush failure at stop 9 stops the run before the answer goes to stdout. SessionStore.flush() waits for all durability listeners, then throws the first listener failure (packages/core/session/src/index.ts:1346-1357). The apply() function of the runner catches the error from run() (packages/bundle/headless/src/index.ts:464). Then fail() writes the error to stderr and requests exit code 1 (packages/bundle/headless/src/index.ts:308-313).

Why it matters. A script that reads the exit code of a headless run must not treat one agent/error event as a failed run. A flush failure also gives exit code 1, and the events of the run are then possibly not durable.

  2. 2
    Which method actually constructs the new Agent: AgentRegistry.create() or the registered factory?
    medium
    Show answer

    The registered factory. AgentRegistry.create() only looks up that factory and calls its createAgent() (packages/core/agent/src/index.ts:422-425).

  3. 3
    In what order do the three tool-pipeline events run for one tool call?
    medium
    Show answer

    tools/pre-execute, then tools/execute, then tools/post-execute (packages/core/tools/src/pipeline.ts:199-201, packages/core/tools/src/pipeline.ts:299-301, packages/core/tools/src/pipeline.ts:487-489).

  4. 4
    The Agent reports idle, but the headless runner does not stop waiting. Name one reason this can happen.
    hard
    Show answer

    Child work was in progress, so waitForChildren() waited and returned true. Another reason: the Agent became busy again, or the sequence number of the session increased after the idle check (packages/bundle/headless/src/index.ts:424-431; see the deep dive above).
