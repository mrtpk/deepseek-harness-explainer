Jobs, workflows, goals and plan mode

IntermediateDeepSeek Harness conceptsabout 8 min read

Code version: DeepSeek Harness @ ce7073d · 2026-10-30

Before you read

This page uses ideas from these pages:

  • The agent loop and the session log Intermediate
  • Subagents and delegation Intermediate

In one sentence

Background jobs, workflows, goals and plan mode are four optional capabilities a deployment composes beside the agent loop.

The idea#

None of these four pieces is part of the turn/step loop itself. A deployment composes each one separately, and the loop runs the same way without it. A background job (job) lets a tool keep long work alive while the agent continues. A workflow runs a model-written script that starts subagents on the agent's behalf. A goal is a durable objective that can start its own next round. Plan mode only adds guidance text to the model's prompt. It enforces nothing by itself (docs/subsystems/workflow.md:5, packages/plan/plan-mode/src/index.ts:1-7).

An everyday comparison. Think of a project manager's extra tools beside their own to-do list. One is a tracker board for farmed-out background tasks. Another is a flowchart someone wrote once to run a multi-step project. A third is a standing checklist that adds its own next item until the work is done. The last is a sticky note that tells the team that it only plans for now. The comparison stops here. The note has no authority, and the manager's own access rules still decide what can happen.

The picture#

Read panel 1 as a state machine. Only running can become stopping. A job in running or stopping ends in one of the three right-hand states, and these states are final (packages/jobs/jobs/src/view.ts:15-19). Read panel 2 from left to right. The script does not call ctx.subagents directly. The engine host makes the call for the script (packages/workflow/workflow-ptc/src/host.ts:200-220).

In the code#

Step 1: ctx.jobs tracks one producer-owned execution per id#

JobRegistry is an abstract seam. A composition loads an implementation such as the in-process dsh-jobs-local (packages/jobs/jobs/src/index.ts:88-96). A job's status is one of running, stopping, completed, killed or failed (packages/jobs/jobs/src/view.ts:19). Only the owner session can read, list or kill a job that has an owner. A job without an owner is open to all callers (packages/jobs/jobs/src/types.ts:184-190, packages/jobs/jobs-local/src/index.ts:310-314, packages/jobs/jobs-local/src/index.ts:405-414).

Step 2: a workflow script's agent() calls reach the same subagent seam#

ctx.workflowEngine is also an abstract seam, with one engine per context (packages/workflow/workflow/src/index.ts:157-168, docs/subsystems/workflow.md:5). The shipped PTC engine parses the script first. Then it runs the script in a sandboxed Node process under the calling session's file policy (packages/workflow/workflow-ptc/src/index.ts:3, packages/workflow/workflow-ptc/src/index.ts:134-137, packages/workflow/workflow-ptc/src/index.ts:167). Each agent() call in the script becomes one call to subagents.startActivation(). The call uses delivery: 'caller', so the engine gets the child's result back (packages/workflow/workflow-ptc/src/host.ts:200-220).

Step 3: a goal drives its own next round, only while armed#

GoalService keeps the current goal of a session in that session's log (packages/goal/goal/src/index.ts:235-236). The goal phase is active, paused, blocked or complete (docs/subsystems/goal.md:24-30). A separate round driver starts the next round only when the durable phase is active and the process-local activation is armed (packages/goal/goal-round-driver/src/index.ts:105-108). The agent must also be idle, with no competing message in the queue (packages/goal/goal-round-driver/src/index.ts:111-117).

Step 4: plan mode adds a prompt section; it enforces nothing#

ctx.planMode logs one whole-value event, plan/mode (packages/plan/plan-mode/src/index.ts:48-53). It adds a deployment-owned guidance section, plan:policy, only while the selected state is active. The selected state is a pending user selection, or else the logged state (packages/plan/plan-mode/src/index.ts:197-204, packages/plan/plan-mode/src/index.ts:382-384). Sandbox mode and approval policy enforce their own restrictions and do not read plan state (packages/plan/plan-mode/src/index.ts:5-7).

More detail#

A goal's round cap comes from the create request. When the request has no cap, the deployment default applies, and that default is 256 (packages/goal/goal/src/index.ts:211-214, packages/goal/goal/src/index.ts:240). A later edit can change the cap (packages/goal/goal/src/index.ts:342). A resume of a goal that used all its rounds fails with an error that names the limit (packages/goal/goal/src/index.ts:377-381). The in-process job provider adds its own defaults on top of the abstract seam. At most 10 running plus stopping jobs can exist per owner, or in the shared bucket for jobs without an owner (packages/jobs/jobs-local/src/index.ts:47-51). It keeps 256 KiB of live output per job. After a job settles, it keeps 16 KiB plus the bytes that the model did not read yet (packages/jobs/jobs-local/src/index.ts:33-40, packages/jobs/jobs-local/src/index.ts:54-58).

The workflow engine has its own limits for each run. The default limit is 1,000 agent() calls in total. The concurrency limit is min(16, max(1, cores - 2)) when the config leaves it at 0, which is the default (packages/workflow/workflow-ptc/src/index.ts:106-112, packages/workflow/workflow-ptc/src/index.ts:141-144). The subagent provider for the children comes from the engine config (default spawn). Only a specialized host-side caller can override it for a run. The script cannot see or change that choice (packages/workflow/workflow-ptc/src/index.ts:107, packages/workflow/workflow-ptc/src/index.ts:137, docs/subsystems/workflow.md:13). An agent() call can still ask for a model provider and a model for its child (packages/workflow/workflow-ptc/src/host.ts:213-218).

The service does not log a user's plan-mode selection immediately. The selection stays pending until the next accepted in-turn pre-step appends it. A selection made after the last such step of a turn stays pending until a later turn (packages/plan/plan-mode/src/index.ts:209-228, docs/subsystems/plan.md:15).

For the full generated references, see the repository's own docs/subsystems/jobs.md, docs/subsystems/workflow.md, docs/subsystems/goal.md and docs/subsystems/plan.md.

What can go wrong#

An active goal does not always continue on its own

Check activation and phase before you wait for an automatic round. A goal stays active in its durable phase after its process-local activation is disarmed, for example before a driver unloads (packages/goal/goal/src/index.ts:284-296, packages/goal/goal-round-driver/src/index.ts:105-108).

Simplified

This page leaves out the job output ring's pull-versus-push sources. It also leaves out the workflow engine's parallel()/pipeline() combinators and the browser-facing projections for all four capabilities.

Why it matters. Code that waits for the next goal round must check the live activation field and the durable phase. If it checks only the phase, it can wait for a round that the driver does not start (packages/goal/goal-round-driver/src/index.ts:105-108).

Check yourself#

  1. 1
    Which service lets a tool keep a long-running command active while the agent moves on to other work?
    easy
    Show answer

    ctx.jobs. The JobRegistry seam registers as ctx.jobs. It tracks long producer work, such as a bash command, outside the turn/step loop (packages/jobs/jobs/src/index.ts:88-96, packages/jobs/jobs/src/types.ts:179-183).

  2. 2
    Can a workflow script itself choose which subagent provider its agent() calls use?
    medium
    Show answer

    No. The engine gets the subagent provider from its own configuration, or from a specialized caller's override. The script "cannot observe or replace either policy" (packages/workflow/workflow-ptc/src/index.ts:137, docs/subsystems/workflow.md:13).

  3. 3
    A goal's phase is active. Does the round driver always start the next round when the agent is idle?
    medium
    Show answer

    No. The goal's process-local activation must also be armed, and no competing message can be in the queue (packages/goal/goal-round-driver/src/index.ts:105-108, packages/goal/goal-round-driver/src/index.ts:111-117).

  4. 4
    What are the in-process job provider's default per-owner concurrency cap and live output retention?
    hard
    Show answer

    10 running or stopping jobs per owner, and 256 KiB of live ring output per job (packages/jobs/jobs-local/src/index.ts:33-37). These are the provider's own defaults. The abstract seam does not set them.
