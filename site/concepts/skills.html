Skills

IntermediateDeepSeek Harness conceptsabout 7 min read + 1 min deep dives

Code version: DeepSeek Harness @ ce7073d · 2026-10-30

Before you read

This page uses ideas from these pages:

  • Everything is a plugin: Cordis Beginner
  • Tools and MCP servers Intermediate

In one sentence

A skill is discovered through a ranked provider in ctx.skills, then loaded on demand by the model-facing skill tool.

The idea#

Skills are optional, named instruction sets. They are not entries in the session log (docs/subsystems/skills.md:5). ctx.skills is the registry. One or more providers list candidate skills, and the registry merges them into one catalog, by name (packages/skill/skill/src/index.ts:345-356). The shipped local provider scans project and user folders, and each folder kind has a fixed rank (packages/skill/skill-filesystem/src/index.ts:251-271). In one registry layer, a project skill thus wins over a personal skill with the same name (docs/subsystems/skills.md:15).

An everyday comparison. Think of a hotel's binder of house procedures on a shelf, and the shelf's own index card listing every binder's title and one-line summary. A guest reads the index card first, and only pulls one specific binder off the shelf when a task needs it. The comparison stops here. A real index card does not change between visits. A session's skill catalog can change between model steps, because the consumer compares it again before each step (packages/skill/tool-skill/src/index.ts:217-240).

In the code#

Step 1: a provider registers with ctx.skills, and scans its roots in rank order#

The local filesystem provider registers itself with ctx.skills.registerProvider() (packages/skill/skill-filesystem/src/index.ts:135-138). It scans six kinds of root, and each kind has a fixed rank. In order: project-dsh (100), project-agents (200), zero or more custom folders (300), user-dsh (400), user-agents (500), and an opt-in bundled folder (600) (packages/skill/skill-filesystem/src/index.ts:35-39, packages/skill/skill/src/index.ts:28, packages/skill/skill-filesystem/src/index.ts:251-271). The two project roots need a known working directory (packages/skill/skill-filesystem/src/index.ts:253).

Step 2: a session injects the catalog as a system reminder#

Before a model step, dsh-tool-skill reads ctx.skills.snapshot(). It does this only when the agent can see its skill tool (packages/skill/tool-skill/src/index.ts:224-227). It compares the result with the newest catalog that the session still shows. It adds a new catalog message only when the two are different (packages/skill/tool-skill/src/index.ts:233-254). The message is a user message in a <system-reminder> block (packages/skill/tool-skill/src/index.ts:258-263). Only model-invocable skills enter the catalog. Each entry has a name and a shortened description, but not the skill's body (packages/skill/tool-skill/src/index.ts:229-230, packages/skill/tool-skill/src/index.ts:53-61).

Step 3: the model loads one full skill with the skill tool#

The skill tool takes one name argument. It finds the name in the current result of ctx.skills.list(), not in the logged catalog message. It refuses the name if the skill does not permit model invocation. Then it calls ctx.skills.get() and returns the full body (packages/skill/tool-skill/src/index.ts:130-159).

More detail#

Within one layer, the registry selects a duplicate skill name first by rank, then by provider order (docs/subsystems/skills.md:15). The registry also has layers by scope, the same as ctx.tools. An unscoped registration goes into the global layer. A plugin that one agent preset mounts goes into that preset's own layer. The nearest layer's entry wins a duplicate name, and rank does not apply across layers (packages/skill/skill/src/index.ts:345-352). The project root is the nearest ancestor directory that contains .git. If there is none, the provider uses the given working directory (packages/skill/skill-filesystem/src/index.ts:959-968).

The dsh-tool-skill config field catalogDescriptionMaxLength sets the maximum length of a catalog description. Its default is 500 characters (packages/skill/tool-skill/src/index.ts:28, packages/skill/tool-skill/src/index.ts:70-72). A longer description is cut and ends with ... (packages/skill/tool-skill/src/index.ts:411-414). The registry does not cache a full skill body. Each get() call asks the winning provider again, so the local provider reads the current body (docs/subsystems/skills.md:192).

For the full generated service and type reference, see the repository's own docs/subsystems/skills.md.

Deep dive

Invocation policy: four combinations, not one flag

A skill's policy has two independent booleans, modelInvocable and userInvocable. In a local skill file, the frontmatter keys are disable-model-invocation and user-invocable. If a key is not there, both booleans are true (packages/skill/skill-filesystem/src/index.ts:1014-1024). The old camelCase keys, for example modelInvocable, are not accepted. The provider ignores that skill file and logs a warning (packages/skill/skill-filesystem/src/index.ts:1015-1017, packages/skill/skill-filesystem/src/index.ts:838-843).

modelInvocableuserInvocableMeaning
truetrueThe default: the model can load it, and a user can type /name to invoke it (packages/skill/tool-skill/src/index.ts:167-180).
truefalseModel-only: the user-facing skill list leaves it out (packages/api/session-controller/src/skill-catalog.ts:78).
falsetrueUser-only: the skill tool refuses to load it for the model (packages/skill/tool-skill/src/index.ts:142-151).
falsefalseNot in either catalog. Only a trusted caller of ctx.skills.get() can load it (docs/subsystems/skills.md:128).

What can go wrong#

A failed root gives no candidates

Check each configured root before you decide that a skill is missing. A root that the provider cannot read gives no candidates. Thus a lower-priority skill with the same name from another root can answer until the failed root recovers (docs/subsystems/skills.md:77, packages/skill/skill-filesystem/src/index.ts:201-205).

Simplified

This page leaves out remote and embedded skill providers, and the Chokidar file watcher that invalidates the catalog. It also leaves out the session skill catalog that a client can read without a live agent.

Why it matters. If a skill is not in the catalog after an edit, read the log first. The provider logs a warning for a skipped root and for an ignored skill file, for example bad frontmatter (packages/skill/skill-filesystem/src/index.ts:204, packages/skill/skill-filesystem/src/index.ts:842).

Check yourself#

  1. 1
    What does the skill catalog that reaches the model contain?
    easy
    Show answer

    Only the name and the shortened description of each model-invocable skill. It does not contain the body (packages/skill/tool-skill/src/index.ts:229-230, packages/skill/tool-skill/src/index.ts:53-61).

  2. 2
    Which root wins when a project skill and a user skill share the same name?
    medium
    Show answer

    The project skill, if both are in the same registry layer. project-dsh (rank 100) and project-agents (rank 200) both have a lower rank than user-dsh (rank 400) and user-agents (rank 500). A lower rank wins (packages/skill/skill-filesystem/src/index.ts:35-39, packages/skill/skill/src/index.ts:807-810).

  3. 3
    Does the registry cache a skill's full body between calls?
    medium
    Show answer

    No. Each ctx.skills.get() call asks the provider of the winning candidate again. The local provider then reads the current body (docs/subsystems/skills.md:192).

  4. 4
    A skill file sets disable-model-invocation to true, so its policy is modelInvocable false and userInvocable true. Can the model's skill tool load it?
    hard
    Show answer

    No. The skill tool checks isModelInvocable two times: on the listed summary and on the loaded definition. It refuses the call if either check is false (packages/skill/tool-skill/src/index.ts:142-151). Only a user's /name can load this skill (packages/skill/tool-skill/src/index.ts:179-180).
