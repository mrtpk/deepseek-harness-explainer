Approval and human interaction

IntermediateDeepSeek Harness conceptsabout 6 min read + 1 min deep dives

Code version: DeepSeek Harness @ ce7073d · 2026-10-30

Before you read

This page uses ideas from these pages:

  • Sandbox and execution Intermediate

In one sentence

ctx.approval decides one yes-or-no question per action and fails closed when nobody answers.

The idea#

Approval answers one question at the moment a tool wants to act: may this specific action proceed (docs/subsystems/approval.md:5)? Sandbox mode is different. It sets the file effects of all calls under a mode before the calls run. Approval decides one call, once, and it asks composed answerers for the decision. ctx.approval owns the full exchange. It logs the ask, asks the answerers, logs the outcome, and returns the outcome to the caller (packages/interaction/user-approval/src/index.ts:242-261).

An everyday comparison. Think of a doorman who approves the entry of one visitor now. A building policy, in contrast, applies to all visitors before they arrive. The comparison stops here. The approval question does not copy the tool arguments. It can name the tool call that the user already sees, through an optional callId (packages/interaction/user-approval/src/index.ts:124-141).

The picture#

Read panel 1 from left to right. In the tool pipeline, a decision of kind ask is the trigger. The audit and the decision occur inside ctx.approval. Read panel 2 as two policies. "never" decides before an answerer runs. "ask" gives the request to the composed answerers in registration order.

In the code#

Step 1: a kind-ask decision reaches ctx.approval.request()#

A tools/pre-execute listener, such as a hook, can return { kind: 'ask' } instead of an allow or a deny (packages/core/tools/src/events.ts:18, packages/core/tools/src/contracts.ts:357-361). The tool pipeline then calls ctx.approval.request() and maps the outcome back. Only allowed-once proceeds. The other three outcomes each deny with their own reason (packages/core/tools/src/pipeline.ts:449-471). When the deployment has no approval service, or the call has no agent, the pipeline denies the call (packages/core/tools/src/pipeline.ts:436-448).

Step 2: the session's policy decides before any answerer runs#

Inside request(), decide() checks the session's effective policy first. A 'never' policy returns rejected before the answerer waterfall starts (packages/interaction/user-approval/src/index.ts:293-318). The service itself does this check. Thus an answerer added later with prepend cannot bypass it (packages/interaction/user-approval/src/index.ts:296-301).

Step 3: one answerer claims the request, or passes it on#

An 'ask' policy runs a waterfall of composed answerers for the agent, in registration order (packages/interaction/user-approval/src/index.ts:306-310, docs/cordis-primer.md:22). An answerer that does not own the agent calls next(). When no answerer claims the ask, the result is unavailable (packages/interaction/user-approval/src/index.ts:309). The ACP automation bridge is one example. It sends a session/request_permission call to its connected client (packages/acp/acp/src/index.ts:158-176).

More detail#

The default policy is 'ask'. A deployment can set 'never' for unattended or CI use (packages/interaction/user-approval/src/index.ts:153-159, packages/interaction/user-approval/src/index.ts:170-172). A session can override the policy at runtime. setPolicy() appends the new approval/policy event. Then it injects a user message that tells the model about the switch (packages/interaction/user-approval/src/index.ts:211-222). allowed-once is a one-shot grant for one ask (packages/interaction/user-approval/src/types.ts:28-32). The service keeps no grant for later calls (packages/interaction/user-approval/src/index.ts:242-261).

The same seam decides a sandbox escalation, the retry that the sandbox page describes. After a sandbox denial, a tool can ask for one retry under a strictly wider mode. The tool sends that ask through ctx.approval.request() (packages/sandbox/sandbox/src/escalation.ts:1-14). This page covers the general approval decision. The sandbox page tells what "strictly wider" means.

For the full generated service and event reference, see the repository's own docs/subsystems/approval.md.

Deep dive

What each closed outcome means to the caller

A tool call does not see the raw return value of an answerer. It sees one of four normalized outcomes (packages/interaction/user-approval/src/types.ts:28-32, packages/interaction/user-approval/src/index.ts:311-318):

OutcomeWhere it comes fromWhat the tool pipeline does
allowed-oncean answerer grants this one actionproceeds (packages/core/tools/src/pipeline.ts:458)
rejectedan answerer declines, or the policy is 'never'denies, "the user rejected ..." (packages/core/tools/src/pipeline.ts:459-462)
cancelledthe request's own signal aborts before or during the ask (packages/interaction/user-approval/src/index.ts:295, packages/interaction/user-approval/src/index.ts:319-324)denies, marked cancelled (packages/core/tools/src/pipeline.ts:463-466)
unavailableno answerer claims the ask, an answerer throws, or an answerer returns an unknown valuedenies, "no approval channel is available" (packages/core/tools/src/pipeline.ts:467-470)

What can go wrong#

approval.request() throws outside an open turn

Call ctx.approval.request() only inside an open turn of the requesting session. Outside a turn, it throws an Error and returns no decision. The audit pair must stay inside the turn boundary of the durable log (packages/interaction/user-approval/src/index.ts:242-250).

Simplified

This page leaves out cancellation races against a live signal, scope-filtered dispatch to the right agent, and the SDK's own opt-in approval/request bridge.

Why it matters. A missing or throwing answerer does not grant an action. The service changes the result to unavailable (packages/interaction/user-approval/src/index.ts:306-318). The tool pipeline and the sandbox escalation deny on each outcome except allowed-once (packages/core/tools/src/pipeline.ts:457-471, docs/subsystems/approval.md:5). The service fails closed, so a caller cannot forget this check.

Check yourself#

  1. 1
    What are the four closed outcomes ctx.approval.request() can return?
    easy
    Show answer

    allowed-once, rejected, cancelled, and unavailable (packages/interaction/user-approval/src/types.ts:28-32). Only allowed-once is a grant.

  2. 2
    A session's approval policy is 'never'. Does any composed answerer see the request?
    medium
    Show answer

    No. decide() returns rejected before the answerer waterfall starts, so no answerer gets the ask (packages/interaction/user-approval/src/index.ts:301).

  3. 3
    How does approval differ from sandbox mode?
    medium
    Show answer

    Sandbox mode sets the file effects of all calls under a mode before the calls run (Sandbox and execution). Approval decides one specific action, once, at the time of the ask (docs/subsystems/approval.md:5).

  4. 4
    A composed answerer throws an exception while deciding. What outcome does request() return, and what does the tool pipeline do with it?
    hard
    Show answer

    unavailable. The service changes a throw to the fail-closed outcome (packages/interaction/user-approval/src/index.ts:315-317). The tool pipeline then denies the call with "no approval channel is available" (packages/core/tools/src/pipeline.ts:467-470).
