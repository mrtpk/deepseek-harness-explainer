The agent loop and the session log

IntermediateDeepSeek Harness conceptsabout 8 min read + 1 min deep dives

Code version: DeepSeek Harness @ ce7073d · 2026-10-30

Before you read

This page uses ideas from these pages:

  • Everything is a plugin: Cordis Beginner
  • Turn, step, round: the session vocabulary Beginner

In one sentence

An Agent runs one session's turn/step loop and appends each turn and step boundary to the session log.

The idea#

A running dsh agent is not one object that does everything. Three pieces share the work. AgentRegistry is the directory: it finds the live agent for a session id, and it accepts only one live agent for each id (packages/core/agent/src/index.ts:591-593, packages/core/agent/src/index.ts:486-492). The agent itself drives the work: it claims input, calls the model, and runs the tools the model asks for, one turn at a time. The session log is the record. The agent appends each turn and step boundary, and each message, to the log as the work occurs (packages/core/agent-loop/src/agent.ts:336, packages/core/agent-loop/src/agent.ts:576). Turn, step, round: the session vocabulary names this vocabulary; Profiles and bundles: how a running dsh tree is assembled shows how a profile assembles the plugins behind these three pieces.

An everyday comparison. Think of a help desk. The registry is the phone system that connects you to an agent. The agent is the person who does the work. The log is the ticket system: it records each action of the agent, in order. The comparison stops here. A help-desk ticket only records work. The session log is different: the model history for the next request comes from it (docs/architecture.md:124).

In the code#

Step 1: AgentRegistry delegates creation to the registered factory#

AgentRegistry does not build agents itself. Its create() method reads the one factory registered with setFactory() and calls that factory's createAgent() (packages/core/agent/src/index.ts:416-426).

Exactly one factory at a time

setFactory() throws if a factory is already registered, so only one component can create agents in a given context (packages/core/agent/src/index.ts:385). The agent-loop package is the factory that registers itself (packages/core/agent-loop/src/index.ts:336).

Step 2: the agent-loop factory builds a ReactLoopAgent#

AgentLoop implements the factory interface (packages/core/agent-loop/src/index.ts:291). Its createAgent() prepares the session, then builds the new agent through initializeAgent() (packages/core/agent-loop/src/index.ts:717-718, packages/core/agent-loop/src/index.ts:734). resume() uses the same initializeAgent() (packages/core/agent-loop/src/index.ts:819). initializeAgent() constructs a ReactLoopAgent for that session (packages/core/agent-loop/src/index.ts:573-577). ReactLoopAgent is the class that implements the Agent interface (packages/core/agent-loop/src/agent.ts:112).

Step 3: the Agent's turn() loop appends to the session log#

Once built, the ReactLoopAgent drives its own work. Its private turn() method opens with a logged turn/start event (packages/core/agent-loop/src/agent.ts:327-340). Then it loops over zero or more steps until nothing is left to do (packages/core/agent-loop/src/agent.ts:344).

The loop appends each of these events through the same Session.append() method (packages/core/session/src/index.ts:806). It assigns the event the next sequence number, then pushes it onto the in-memory log (packages/core/session/src/index.ts:829, packages/core/session/src/index.ts:901).

More detail#

Creation happens in order. AgentRegistry.create() reads the factory and calls createAgent() (packages/core/agent/src/index.ts:425). The agent-loop's createAgent() prepares the session, then hands off to initializeAgent(), which constructs the new ReactLoopAgent (packages/core/agent-loop/src/index.ts:573). initializeAgent() then publishes the agent in the registry with agents.enter() (packages/core/agent-loop/src/index.ts:636). After that, the registry only tracks the live Agent; the ReactLoopAgent instance drives every turn itself.

Inside one turn, each step opens with a logged step/start event. It always closes with a logged step/end event, even if the step throws, because the loop appends step/end in a finally block (packages/core/agent-loop/src/agent.ts:361, packages/core/agent-loop/src/agent.ts:386-389). The loop runs another step in two cases. In the first case, the step ran tool calls and the tool batch did not conclude the turn, so the step returns no end reason (packages/core/agent-loop/src/agent.ts:597). In the second case, new input waits in the next-step inbox (packages/core/agent-loop/src/agent.ts:395). Otherwise, the loop waits for the agent/turn-stopping listeners. If the inbox is still empty after them, the loop closes the turn with a logged turn/end event (packages/core/agent-loop/src/agent.ts:395-399, packages/core/agent-loop/src/agent.ts:422).

One exception applies to the first case. After one step of a turn hits the max-tokens limit, that end reason stays for the rest of the turn (packages/core/agent-loop/src/agent.ts:373). A later step that ran tool calls then does not start another step by itself (packages/core/agent-loop/src/agent.ts:395-399). Each step also renders a system prompt and calls the model through ctx.llm (packages/core/agent-loop/src/agent.ts:442, packages/core/agent-loop/src/agent.ts:490); The LLM seam and the system prompt reads that seam in detail.

One config knob changes how many parallel-safe tool calls inside a step can run at the same time: maxParallelToolCalls (packages/core/agent-loop/src/constants.ts:5-6). The loop reads its live value in each step that has tool calls (packages/core/agent-loop/src/agent.ts:586-593). Its default is 10. The agent-loop package sets this constant once and applies it through its config schema (packages/core/agent-loop/src/constants.ts:6, packages/core/agent-loop/src/index.ts:296). The schema marks the value as volatile, so a deployment can change it while the agent runs. A live change applies from the next tool batch (docs/upgrade-guide/v0.2.1-rc.2/tool-executor-plugins/guide.md:17). Tools and MCP servers reads how each of those tool calls runs through its own pipeline.

For the full generated service and event reference, see the repository's own docs/subsystems/core.md and docs/subsystems/session.md.

Deep dive

Exact conditions that close a turn

"The turn ends" is not one condition. The loop has four kinds of exit. A finally block appends turn/end with the reason that the exit set (packages/core/agent-loop/src/agent.ts:419-422):

  1. Blocked. Only when a pre-step listener rejects the claimed input: the loop sets reason blocked and stops before it runs a step (packages/core/agent-loop/src/agent.ts:348-350).
  2. Completed with no step spent. Only on the turn's first claim, when its message list is empty: the turn closes as completed with no model call (packages/core/agent-loop/src/agent.ts:356-358).
  3. Normal end. After a step that returned an end reason (completed or max-tokens), only when the next-step inbox is empty after the agent/turn-stopping listeners (packages/core/agent-loop/src/agent.ts:395-399). The reason is the step's end reason (packages/core/agent-loop/src/agent.ts:373). A later claim with an empty message list also ends the turn this way (packages/core/agent-loop/src/agent.ts:353).
  4. Error or cancellation. When the turn throws, the reason is aborted if the abort signal fired, and error in all other cases (packages/core/agent-loop/src/agent.ts:402-418).

What can go wrong#

A turn can close without running a single step

Check for a logged step before you assume the model was called. A turn can end as completed on its very first claim, only when that claim's message list is empty (packages/core/agent-loop/src/agent.ts:356-358). A blocked turn also has no step (packages/core/agent-loop/src/agent.ts:348-350).

Simplified

This page leaves out tool-call recovery after a failed step, retries, and cancellation. When a step throws, the loop still appends any tool results it already owes before it re-throws the error (packages/core/agent-loop/src/agent.ts:374-385).

Why it matters. Code that reads the session log to reconstruct what the agent did must handle a turn with zero steps.

Check yourself#

  1. 1
    Which object builds the live ReactLoopAgent: AgentRegistry or the agent-loop factory?
    easy
    Show answer

    The agent-loop factory (AgentLoop). AgentRegistry.create() only looks up the registered factory and calls its createAgent() (packages/core/agent/src/index.ts:425).

  2. 2
    Does every turn call the model at least once?
    medium
    Show answer

    No. A turn can close as completed on its first claim with no step spent, when that claim has an empty message list (packages/core/agent-loop/src/agent.ts:356-358). A turn that a pre-step listener blocks also ends before any step (packages/core/agent-loop/src/agent.ts:348-350).

  3. 3
    What happens to the step/end event if a step throws an error?
    medium
    Show answer

    The loop still appends it. The loop appends step/end in a finally block, so this occurs when the step succeeds and when it throws (packages/core/agent-loop/src/agent.ts:386-389).

  4. 4
    Which config value changes how many tool calls in one step run at the same time, and where is its default set?
    hard
    Show answer

    maxParallelToolCalls. It limits the parallel-safe calls of one step. Its default (10) is a constant in the agent-loop package, applied through its config schema (packages/core/agent-loop/src/constants.ts:6, packages/core/agent-loop/src/index.ts:296), and read live in each step that has tool calls (packages/core/agent-loop/src/agent.ts:588).
