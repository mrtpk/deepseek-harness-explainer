The LLM seam and the system prompt

IntermediateDeepSeek Harness conceptsabout 6 min read + 1 min deep dives

Code version: DeepSeek Harness @ ce7073d · 2026-10-30

Before you read

This page uses ideas from these pages:

  • Everything is a plugin: Cordis Beginner
  • The agent loop and the session log Intermediate

In one sentence

ctx.llm streams one model call through a registered provider adapter, after the agent assembles a system prompt from ordered sections.

The idea#

The agent loop sends each model call through one service: ctx.llm. ctx.llm does not talk to a provider itself. An object called a provider adapter does that work. ctx.llm selects the adapter registered for the request's provider name (packages/llm/llm/src/index.ts:401, packages/llm/llm/src/index.ts:1167).

Before the loop calls ctx.llm, it builds that request's system prompt. Plugins register ordered sections with ctx.systemPrompt. One assembly call collects them for the current step, and renderPrompt() makes the text (packages/core/agent-loop/src/agent.ts:294, packages/core/agent-loop/src/agent.ts:442).

An everyday comparison. Think of ctx.llm as a phone switchboard. You dial a provider's name, and the switchboard connects you to the one line registered for it. The system prompt is a briefing note read onto the call first. The comparison stops here. A real briefing note does not change between calls. The system prompt can change, because a section's text can be a function of the current step (packages/core/system-prompt/src/index.ts:61-66).

The picture#

Read panel 1 left to right: the loop does not talk to a provider directly. It goes through ctx.llm to the registered adapter. Read panel 2 left to right, in order: these three sub-steps run before any bytes go to the provider. On a retry, the loop does not assemble again (docs/architecture.md:112). The colours mark one role each; the legend under the diagram names them.

In the code#

Step 1: ctx.llm routes stream() to the adapter registered for one provider name#

A provider adapter extends the abstract LlmAdapter class. A plugin registers it with ctx.llm.registerAdapter(providers, adapter) (packages/llm/llm/src/index.ts:401). DeepSeekAdapter is one such adapter (packages/llm/llm-deepseek/src/adapter.ts:22). The DeepSeek host code registers it for one provider name (packages/llm/llm-deepseek/src/host.ts:81).

Step 2: the agent assembles the system prompt before it builds the request#

Each step's preStep() calls ctx.systemPrompt.assemble() with the step's model selection and the tools admitted for that step (packages/core/agent-loop/src/agent.ts:288-294). renderPrompt() then changes that assembly into plain text (packages/core/agent-loop/src/agent.ts:442).

Step 3: the rendered prompt is committed to the session, not sent as a hidden field#

systemPrompt.project(renderedPrompt, ...) finds what changed since the last step. The loop appends each resulting commit as a system/message session event (packages/core/agent-loop/src/agent.ts:453-461). If nothing changed, there is no commit (packages/core/agent-loop/src/runtime-context.ts:103-106). The system prompt reaches the model as logged history, not as a field only the request carries (docs/architecture.md:112).

Step 4: buildRequest() derives the history and streams the frozen request#

buildRequest() logs a request/header in three cases. The cases are the first step of this loop instance, a header change (config or tools), and a new request series (packages/core/agent-loop/src/agent.ts:675-691). Then it makes the model-visible message list from the session log with session.deriveMessages() (packages/core/agent-loop/src/agent.ts:728). Before this, prepareRequest() got a prepared call from ctx.llm.prepareCall() (packages/core/agent-loop/src/agent.ts:644). The step streams the frozen request through that prepared call. If no adapter is registered for the provider, it uses ctx.llm.stream() (packages/core/agent-loop/src/agent.ts:646-650, packages/core/agent-loop/src/agent.ts:490).

More detail#

registerAdapter() takes every provider name an adapter owns and registers them together, all at once. If one of those names already has an adapter, the call fails with DUPLICATE_ADAPTER and no name is registered (packages/llm/llm/src/index.ts:393-396, packages/llm/llm/src/index.ts:437-444). Both ctx.llm.stream() and a prepared call's stream() run inside the llm/stream waterfall (packages/llm/llm/src/index.ts:1010, packages/llm/llm/src/index.ts:1170-1183). Thus a plugin can wrap each call, for example for retry, before the call gets to the adapter.

A prompt section's order sets the position of its text. Sections join in ascending order, and equal orders use name order (packages/core/system-prompt/src/index.ts:56-60). A duplicate section name in one layer throws, and so does an order that is not finite (packages/core/system-prompt/src/index.ts:477-493). A section can also set complete. Assembly still runs its full waterfall, but then keeps that one section as the whole prompt. Two active complete sections make assembly fail (packages/core/system-prompt/src/index.ts:69-75).

For the full generated service and type reference, see the repository's own docs/subsystems/llm-streaming.md and docs/subsystems/system-prompt.md.

Deep dive

Why the system prompt is a session event, not a request field

Many APIs send a system prompt as one field on each request. DeepSeek Harness instead keeps it in the durable session history. Thus a reader of the session log can see the system prompt that the model got (docs/architecture.md:112).

By default, the loop appends a new system/message event that replaces the first system node in the model-visible history. It also clears later system nodes (packages/core/agent-loop/src/runtime-context.ts:100-104, packages/core/agent-loop/src/runtime-context.ts:110-114). The other route applies only when the prepared call has systemPromptUpdate: 'in-history'. Then the loop appends each change as a new system node (packages/core/agent-loop/src/agent.ts:453-454, packages/core/agent-loop/src/runtime-context.ts:106-107). Even on that route, the start of a new request series with a changed prompt uses the replace path (packages/core/agent-loop/src/runtime-context.ts:100).

What can go wrong#

A step cannot change its provider or model through agent/request

To change the provider, model or reasoning effort, call agent.model.select() before step preparation. The deprecated agent/request hook throws if its decision is different from the selection that step preparation already fixed (packages/core/agent-loop/src/agent.ts:635-640, docs/architecture.md:112).

Simplified

This page leaves out dsh-llm-retry's retry policy, image-attachment pricing and resizing, and reasoning-effort validation. It also leaves out what happens when no adapter is registered for a request's provider name.

Why it matters. To make a model call again from the session log, read the system/message events. Do not look for a separate system field.

Check yourself#

  1. 1
    Which method must every provider adapter implement?
    easy
    Show answer

    stream(). It is the only abstract method of LlmAdapter. The other methods have a default (packages/llm/llm/src/index.ts:208, packages/llm/llm/src/index.ts:297-302).

  2. 2
    Does the system prompt reach the model as a hidden request field?
    medium
    Show answer

    No. The loop commits it as a system/message session event. Thus it is logged history, not a field that only the request carries (packages/core/agent-loop/src/agent.ts:453-461, docs/architecture.md:112).

  3. 3
    What happens when two provider adapters try to register the same provider name?
    medium
    Show answer

    The second registration fails with DUPLICATE_ADAPTER. Registration is all-or-nothing for the adapter's full provider list (packages/llm/llm/src/index.ts:393-396, packages/llm/llm/src/index.ts:442-443).

  4. 4
    Can the deprecated agent/request hook change which provider or model a step calls?
    hard
    Show answer

    No. preStep() always fixes a selection first, and it throws if there is none (packages/core/agent-loop/src/agent.ts:288-291). agent/request throws if its proposed config has a different provider, model or effort (packages/core/agent-loop/src/agent.ts:635-640). The hook can change only the other request controls (docs/architecture.md:112).
