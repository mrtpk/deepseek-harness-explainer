ACP, SDKs and clients

IntermediateDeepSeek Harness conceptsabout 6 min read

Code version: DeepSeek Harness @ ce7073d · 2026-10-30

Before you read

This page uses ideas from these pages:

  • The agent loop and the session log Intermediate

In one sentence

A client reaches dsh through the ACP server, the SDK wire protocol, or the Web and Desktop connection layer.

The idea#

dsh has three separate protocol seams for three kinds of client. The ACP server speaks a standard, automation-only JSON-RPC protocol over stdio. It intentionally leaves out DSH-specific presentation data and interactive UI features (packages/acp/acp/README.md:2, packages/acp/acp/README.md:12). The SDK wire protocol is dsh's own newline-delimited JSON-RPC. dsh-sdk-jsonrpc-server serves it over stdio, and the TypeScript and Python SDKs speak it (packages/sdk/protocol/README.md:12, packages/sdk/server/README.md:12). Web and Desktop speak Remote RPC. The browser uses HTTP POST for unary calls, and a Gateway-owned WebSocket carries the streams (packages/client/connection/README.md:12, packages/client/connection/README.md:34).

An everyday comparison. Think of a building with three doors: a loading dock for scripted deliveries, a maintenance door for automation, and the main lobby for people. The comparison stops here. In dsh, the profile decides which doors a deployment opens.

The picture#

Read panel 1 as three independent doors into the same session and agent-loop core. Each door is its own plugin. Read panel 2 as a special case of the SDK seam. The Python SDK adds no protocol of its own.

In the code#

Step 1: the ACP server exposes a fixed set of session methods#

initialize() reports one protocol version. It also reports the session capabilities that this server adds to the ACP v1 baseline: close, list and resume (packages/acp/acp/src/index.ts:179-193). One connection can run several independent sessions at the same time (packages/acp/acp/README.md:60).

Step 2: the SDK wire protocol is one JSON-RPC message per line#

Both wire ends of the SDK protocol use one rule: one JSON-RPC 2.0 message per newline-terminated line over a byte stream (packages/sdk/protocol/README.md:34). The TypeScript client finds the same-version @deepseek-ai/dsh executable, unless the caller gives one in dshBin. The client owns that subprocess and reaps it on close() (packages/sdk/client/README.md:12).

Step 3: the Python SDK launches the same binary; it has no protocol of its own#

The Python SDK drives DeepSeek Harness as a subprocess, over the same newline-delimited JSON-RPC on stdio (python/README.md:5). It has no separate application entrypoint. It launches the bundled dsh CLI with --profile sdk. That profile owns the JSON-RPC server, agent composition, and persistence (python/sdk/README.md:31).

Step 4: Web and Desktop share one connection carrier#

The browser sends Remote RPC calls over HTTP POST. A Gateway-owned WebSocket carries the streams (packages/client/connection/README.md:34). Desktop uses the same connection package. Its page gets the HTTP origin of its own Host as streamBaseUrl. The Gateway uses that origin for its WebSocket (packages/client/connection/README.md:30, apps/desktop/src/main.ts:790).

More detail#

A different bundle mounts each seam. The acp-app bundle mounts dsh-acp (packages/bundle/acp-app/cordis.patch.yml:15-16). The sdk-app and sdk-minimal bundles mount dsh-sdk-jsonrpc-server (packages/bundle/sdk-app/cordis.patch.yml:17-18, packages/bundle/sdk-minimal/cordis.patch.yml:11-12). The web-app bundle mounts dsh-client-connection (packages/bundle/web-app/cordis.patch.yml:230-231). The sdk-app bundle also mounts the connection package, but it starts no Web server (packages/bundle/sdk-app/cordis.patch.yml:46-49). The profiles page tells how a profile assembles its plugin tree.

ACP and the SDK server each register an answerer on the approval waterfall that the approval page describes. The ACP answerer handles each ask for its own agents that has a tool-call id (packages/acp/acp/src/index.ts:158-160). The SDK answerer works only when the client sets approvalRequests in initialize (packages/sdk/server/src/server.ts:130-131, packages/sdk/server/src/server.ts:258).

The two automation protocols set the model route differently. ACP's provider and model are plugin config. They are the start route of each session that the server makes (packages/acp/acp/README.md:47-48). An ACP client can then change the model or reasoning_effort of one session with session/set_config_option (packages/acp/acp/README.md:70, packages/acp/acp/src/model-control.ts:30-34). The SDK sets its route for each connection, in the initialize handshake, with an optional reasoningEffort and maxTokens (packages/sdk/client/README.md:79).

No single generated subsystems page covers all three seams. The package READMEs cited above are the deeper reference. The repository's own docs/subsystems/web-client.md covers the Web Client architecture.

What can go wrong#

A bad dsh executable or route fails the SDK handshake

The TypeScript client finds the same-version @deepseek-ai/dsh executable, unless dshBin names one (packages/sdk/client/README.md:12). start() runs a bounded initialize handshake. The server checks the route before it accepts prompts. The default handshake timeout is 10 seconds, and the error names the profile and the stderr tail (packages/sdk/client/README.md:79).

Simplified

This page leaves out MCP server mounting, session persistence and resume, image-prompt support, and the exact Remote RPC attachment format.

Why it matters. No SDK runs the harness inside the caller's process. The TypeScript client and the Python SDK each start a dsh subprocess (packages/sdk/client/README.md:12, python/sdk/README.md:31). Thus each client instance talks to its own runtime process.

Check yourself#

  1. 1
    Which of the three protocol seams is automation-only and intentionally leaves out DSH-specific presentation data?
    easy
    Show answer

    The ACP server. It exposes only the standard ACP v1 surface (packages/acp/acp/README.md:12, packages/acp/acp/README.md:32).

  2. 2
    Does the Python SDK define its own wire protocol?
    medium
    Show answer

    No. It launches the bundled dsh --profile sdk binary. It speaks the same newline-delimited JSON-RPC-on-stdio protocol that the SDK server serves (python/README.md:5, python/sdk/README.md:31).

  3. 3
    How does the Desktop app's page reach its own local Host, and not a remote Web deployment?
    medium
    Show answer

    The Desktop main process gives the page the origin of its own Host as streamBaseUrl. The Gateway uses that origin for its WebSocket. The HTTP transport is selected separately (packages/client/connection/README.md:30, apps/desktop/src/main.ts:790).

  4. 4
    An ACP deployment sets provider and model in plugin config. Can an ACP client run one session on a different model?
    hard
    Show answer

    Yes. The config gives the start route of each new session (packages/acp/acp/README.md:47-48). A client can then send session/set_config_option with the advertised model option. The change applies from that agent's next model step (packages/acp/acp/README.md:70, packages/acp/acp/src/model-control.ts:30-34). In the SDK, the client sets the route in its initialize handshake (packages/sdk/client/README.md:79).
