Profiles and bundles: how a running dsh tree is assembled

BeginnerLearn the basicsabout 6 min read

Code version: DeepSeek Harness @ ce7073d · 2026-10-30

Before you read

This page uses ideas from these pages:

  • Everything is a plugin: Cordis Beginner

In one sentence

A profile stacks ordered bundles; patch files then overlay the result, in a fixed order, to build one running dsh plugin tree.

The idea#

A running dsh is a plugin tree put together at boot (docs/architecture.md:15). A profile is the named composition: it lists the bundles it stacks and keeps the user's own patch file (docs/architecture.md:17). A bundle ships Cordis config rows, and the code that mounts them, in a form the layers above it can still change (docs/architecture.md:19). Everything is a plugin: Cordis already showed that every part of dsh, including a bundle's own code, is a plugin.

An everyday comparison. Think of a profile as a packing list, and each bundle as a sealed box on that list. The boxes stack in a fixed order. A patch file is a note taped on top of the stack. It can replace the whole content of one named box, or add a new box. The comparison stops here. A real note cannot reopen a sealed box, but a patch file can replace a row's whole configuration.

The picture#

Read panel 1 as two examples of the same bundle list format. Read panel 2 top to bottom: each layer applies after the one above it. A later layer wins when both touch the same row id. The colours mark one role each; the legend under the diagram names them.

In DeepSeek Harness#

The shipped profile templates are plain data. web stacks dsh-base and dsh-web-app; headless stacks dsh-base and dsh-headless (packages/util/official-bundles/src/bundles.ts:14-19). A bundle names its own patch file in its package.json, under a dsh field. The headless bundle points dsh.bundle.patch at ./cordis.patch.yml (packages/bundle/headless/package.json:39-42).

When dsh boots a profile, readProfilePatches() builds the full, ordered patch list. It reads every bundle's own patches first, then the profile's own cordis.patch.yml. Next comes the home-level $DSH_HOME/cordis.patch.yml, then the --patch files from the command line (packages/boot/app-boot/src/profile-context.ts:75-80).

Turn, step, round: the session vocabulary names the turn/step vocabulary that the resulting tree runs. The agent loop and the session log reads one of the services this tree mounts.

More detail#

composeEntries() applies every layer's patches, in the order above, over an empty entry list (packages/boot/app-boot/src/profile.ts:755-762). A patch names a row by its id: it either replaces that row's whole configuration, or inserts a new row (docs/architecture.md:25). Because later layers apply last, a --patch file can override a setting the home-level patch also touches. The home-level patch can, in turn, override a setting the profile's own cordis.patch.yml sets.

One config knob changes where the home-level patch file is read from: the DSH_HOME environment variable. resolveDshHome() reads it, and falls back to ~/.dsh when it is not set (packages/util/home-paths/src/index.ts:18, packages/util/home-paths/src/index.ts:127-128, packages/util/home-paths/src/index.ts:135-137). The boot code reads the home-level patch from that directory (apps/cli/src/profile-boot.ts:320). The --patch <path> flag is repeatable: each use adds one more overlay file, applied in the order given on the command line (apps/cli/src/args.ts:26, apps/cli/src/args.ts:170).

To see the exact tree one invocation mounts, run dsh --profile web --dump-config. Any row it prints can be replaced by a patch of your own (docs/architecture.md:31-37). For the full generated API reference, see the repository's own docs/subsystems/boot.md.

What can go wrong#

Check all four layers before you assume a setting is wrong

A setting that looks wrong may come from a layer you did not check. The home-level $DSH_HOME/cordis.patch.yml outranks the profile's own patch file, and a --patch overlay outranks both (packages/boot/app-boot/src/profile-context.ts:75-80). Run --dump-config to see the composed result instead of reading each file by hand.

Simplified

This page leaves out presets, hot-module reload of patch files, and platform-gated bundles. It also leaves out how an unreadable or incompatible bundle is skipped instead of failing the boot. After the four layers, boot can append one more patch that disables the telemetry row. This occurs only when DSH_TELEMETRY_DISABLED is not empty (packages/boot/app-boot/src/profile-context.ts:81-83, packages/boot/app-boot/src/profile-context.ts:52-54). Cordis itself is explained only as the framework these bundles and patches build on (vendor/cordis/).

Why it matters. When a plugin seems to be missing, check every patch layer for a disabled: true row with the plugin's row id. Do not check only the profile's own patch file.

Check yourself#

  1. 1
    What does a profile list, and what does a bundle ship?
    easy
    Show answer

    A profile lists the bundles it stacks (docs/architecture.md:17). A bundle ships Cordis config rows and the code that mounts them (docs/architecture.md:19).

  2. 2
    In which order does dsh apply these: the home-level patch, a bundle's own patch, a --patch overlay, and the profile's own patch file?
    medium
    Show answer

    A bundle's own patch, then the profile's own cordis.patch.yml, then the home-level patch, then a --patch overlay (packages/boot/app-boot/src/profile-context.ts:75-80).

  3. 3
    Which two bundles does the shipped headless profile stack?
    medium
    Show answer

    dsh-base and dsh-headless (packages/util/official-bundles/src/bundles.ts:17-19).

  4. 4
    A row id is set by both the home-level patch and a --patch overlay. Which value wins, and why?
    hard
    Show answer

    The --patch overlay's value. readProfilePatches() appends the --patch overlays after the home-level patch (packages/boot/app-boot/src/profile-context.ts:75-80). composeEntries() then applies every layer's patches over the previous result, in that order (packages/boot/app-boot/src/profile.ts:755-762). The last patch for a row id wins.
