Plugins contribute services, typed events and reversible effects to a shared context. --- DeepSeek Harness has no privileged core: every part of it, including the agent loop itself, is a {{term plugin}} mounted on {{term cordis}}.

The idea

DeepSeek Harness (dsh) is an open-source agent harness ({{cite README.md:5}}). It is built on an "everything-is-a-plugin" architecture and powered by Cordis ({{cite README.md:7}}). Every part of the product, including the agent loop itself, is a plugin, and there is no privileged core ({{cite docs/architecture.md:9}}, {{cite docs/architecture.md:11}}). A {{term plugin}} is an object that implements Service ({{cite docs/cordis-primer.md:9}}). A {{term service}} claims a stable key on a shared {{term context}}, and other plugins find it by that key instead of by import ({{cite docs/cordis-primer.md:10}}).

An everyday comparison. Think of a context as a shared toolbox on a workbench. A plugin does not keep its own private copy of a tool. It reaches into the toolbox and asks for the tool by name, for example ctx.tools or ctx.llm ({{cite docs/cordis-primer.md:10}}). The comparison stops here: a toolbox does not notify anyone when a tool is put back. A Cordis context does: plugins can also tell each other about things that happened, through events.

In DeepSeek Harness

The one-shot headless runner is an ordinary plugin. It exports a name, an inject list of the services it needs, and an apply(ctx, config) function ({{cite packages/bundle/headless/src/index.ts:42}}, {{cite packages/bundle/headless/src/index.ts:45}}, {{cite packages/bundle/headless/src/index.ts:456}}). AgentRegistry.setFactory() shows a typical {{term effect | reversible effect}}. It registers inside ctx.effect() and returns the exact disposer that clears the registration again ({{cite packages/core/agent/src/index.ts:384-392}}, {{cite packages/core/agent/src/index.ts:398}}). The tool pipeline shows a typical {{term typed-event | typed event}}. Before a tool runs, ctx.tools dispatches tools/pre-execute as a waterfall event ({{cite packages/core/tools/src/pipeline.ts:199-201}}). A listener can inspect or change the decision before the next listener runs ({{cite docs/cordis-primer.md:31-33}}). The next page, {{link learn/profiles-and-bundles}}, shows how many such plugins stack into one running tree. {{link concepts/agent-loop-and-session}} and {{link concepts/tools-and-mcp}} each read one of these services in detail.

More detail

A plugin that needs another service names it in inject. Cordis waits until every required service exists before the plugin's apply() runs. Load order comes from service dependencies, not from a manual boot sequence ({{cite docs/cordis-primer.md:11}}). By convention, one domain owns one service key. A tool-pipeline event belongs to ctx.tools. Model streaming belongs to ctx.llm, and live agent coordination belongs to ctx.agents ({{cite docs/cordis-primer.md:43}}).

Typed events do not all dispatch the same way. Cordis has five dispatch modes: emit, waterfall, parallel, serial, and bail. Each event picks one mode as part of its contract ({{cite docs/cordis-primer.md:19-25}}). A waterfall listener, such as a tools/pre-execute handler, must call next() to pass its result on. Returning without it stops the chain there ({{cite docs/cordis-primer.md:29-30}}). One config knob changes what a running tree contains: a patch file can turn a whole row off with disabled: true. The headless bundle's own patch does this to four rows it does not need for a one-shot run ({{cite packages/bundle/headless/cordis.patch.yml:35-46}}).

For the generated service and event reference, see the repository's own {{cite docs/subsystems/core.md}} and the {{cite docs/cordis-primer.md}} primer this page is based on.

Every typed event picks one mode. The mode decides whether Cordis waits for listeners, what order they run in, and whether a listener can return a value ({{cite docs/cordis-primer.md:19-25}}).

tools/pre-execute is a waterfall event. Listeners run in registration order, not all at once. The result is the decision the tool pipeline uses ({{cite packages/core/tools/src/pipeline.ts:199-202}}).

The "Awaited?" column is the primer's own column. A waterfall dispatch returns the value of the listener chain. When that value is a promise, the caller can await it: the tool pipeline awaits the tools/pre-execute result ({{cite packages/core/tools/src/pipeline.ts:199}}).

What can go wrong

Before you assume a plugin is broken, look for a disabled: true row that provides a service the plugin injects. A plugin runs its apply() only when every required service it injects exists ({{cite docs/cordis-primer.md:11}}). If a patch disables the only provider of that service, the plugin's apply() does not run.

This page leaves out isolation (a plugin's own sub-context), hot-module reload, and the exact mounting algorithm. Cordis itself ({{cite vendor/cordis/}}) is vendored by source copy ({{cite vendor/README.md:1-5}}). This site explains it only as the interface DeepSeek Harness plugins build on.

Why it matters. When a feature seems to do nothing, check which services its plugin injects, and whether the profile's bundle stack still provides all of them.

What does a plugin claim from a context, instead of importing another plugin's code directly?

A service, found by a stable key such as ctx.tools or ctx.llm ({{cite docs/cordis-primer.md:10}}).

 How does a plugin make sure another plugin's service is ready before it runs?

It names the service in its inject list. Cordis waits until every required service exists before the plugin's apply() runs ({{cite docs/cordis-primer.md:11}}).

 What must a waterfall listener call to pass its result on to the next listener?

next(). Returning without calling it stops the chain at that listener ({{cite docs/cordis-primer.md:29-30}}).

 Which dispatch mode is awaited and runs every listener at once: parallel or waterfall?

parallel. The primer marks it as awaited, with no return value. It marks waterfall as not awaited, with a return value, and its listeners run in registration order (the dispatch-mode table above, {{cite docs/cordis-primer.md:19-25}}).
