A plugin claims services from a shared context, and plugins cooperate only through typed events and reversible effects. --- DeepSeek Harness has no privileged core: every part of it, including the agent loop itself, is a {{term plugin}} mounted on {{term cordis}}.

The idea

DeepSeek Harness (dsh) is an open-source agent harness ({{cite README.md:5}}). It is built on an "everything-is-a-plugin" architecture and powered by Cordis ({{cite README.md:7}}). A {{term plugin}} is an object that claims one or more {{term service | services}} from a shared {{term context}}, instead of importing other code directly ({{cite docs/cordis-primer.md:9-10}}).

An everyday comparison. Think of a context as a shared toolbox on a workbench. A plugin does not keep its own private copy of a tool. It reaches into the toolbox and asks for the tool by name, for example ctx.tools or ctx.llm ({{cite docs/cordis-primer.md:10}}). The comparison stops here: a toolbox does not notify anyone when a tool is put back. A Cordis context does: plugins can also tell each other about things that happened, through events.

In DeepSeek Harness

The one-shot headless runner is an ordinary plugin. It exports a name, an inject list of the services it needs, and an apply(ctx, config) function ({{cite packages/bundle/headless/src/index.ts:42}}, {{cite packages/bundle/headless/src/index.ts:45}}, {{cite packages/bundle/headless/src/index.ts:456}}). AgentRegistry.setFactory() shows a typical {{term effect | reversible effect}}. It registers inside ctx.effect() and returns the exact disposer that clears the registration again ({{cite packages/core/agent/src/index.ts:384-392}}). The tool pipeline shows a typical {{term typed-event | typed event}}. Before a tool runs, ctx.tools dispatches tools/pre-execute as a waterfall event ({{cite packages/core/tools/src/pipeline.ts:199-201}}). A listener can inspect or change the decision before the next listener runs. The next page, {{link learn/profiles-and-bundles}}, shows how many such plugins stack into one running tree. {{link concepts/agent-loop-and-session}} and {{link concepts/tools-and-mcp}} each read one of these services in detail.

More detail

A plugin that needs another service names it in inject. Cordis waits until every named service exists before the plugin's apply() runs. Load order comes from service dependencies, not from a manual boot sequence ({{cite docs/cordis-primer.md:11}}). By convention, one domain owns one service key. A tool-pipeline event belongs to ctx.tools. Model streaming belongs to ctx.llm, and live agent coordination belongs to ctx.agents ({{cite docs/cordis-primer.md:43}}).

A typed event is not one thing. Cordis has five dispatch modes: emit, waterfall, parallel, serial, and bail. Each event picks one mode as part of its contract ({{cite docs/cordis-primer.md:19-25}}). A waterfall listener, such as a tools/pre-execute handler, must call next() to pass its result on. Returning without it stops the chain there ({{cite docs/cordis-primer.md:29-30}}). One config knob changes what a running tree contains: a patch file can turn a whole row off with disabled: true. The headless bundle's own patch does this to four rows it does not need for a one-shot run ({{cite packages/bundle/headless/cordis.patch.yml:35-46}}).

For the generated service and event reference, see the repository's own {{cite docs/subsystems/core.md}} and the {{cite docs/cordis-primer.md}} primer this page is based on.

Every typed event picks one mode. The mode decides whether Cordis waits for listeners, what order they run in, and whether a listener can return a value ({{cite docs/cordis-primer.md:19-25}}).

tools/pre-execute is a waterfall event. Listeners run in registration order, not all at once. The result is the decision the tool pipeline uses ({{cite packages/core/tools/src/pipeline.ts:199-201}}).

What can go wrong

Check the bundle's patch file for a disabled: true row with the same id before you assume a plugin is broken. A plugin runs its apply() only when every service it injects exists ({{cite docs/cordis-primer.md:11}}). If a bundle disables a service a plugin needs, that plugin's apply() never runs.

This page leaves out isolation (a plugin's own sub-context), hot-module reload, and the exact mounting algorithm. Cordis itself ({{cite vendor/cordis/}}) is vendored by source copy ({{cite vendor/README.md:1-5}}). This site explains it only as the interface DeepSeek Harness plugins build on.

Why it matters. When a feature seems to do nothing, check which services its plugin injects, and whether the profile's bundle stack still provides all of them.

What does a plugin claim from a context, instead of importing another plugin's code directly?

A service, found by a stable key such as ctx.tools or ctx.llm ({{cite docs/cordis-primer.md:10}}).

 How does a plugin make sure another plugin's service is ready before it runs?

It names the service in its inject list. Cordis waits until every named service exists before the plugin's apply() runs ({{cite docs/cordis-primer.md:11}}).

 What must a waterfall listener call to pass its result on to the next listener?

next(). Returning without calling it stops the chain at that listener ({{cite docs/cordis-primer.md:29-30}}).

 Which dispatch mode is awaited and runs every listener at once: parallel or waterfall?

parallel. It is awaited and has no return value. waterfall is not awaited, but it does have a return value (the dispatch-mode table above, {{cite docs/cordis-primer.md:19-25}}).
