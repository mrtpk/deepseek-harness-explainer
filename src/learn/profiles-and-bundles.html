This page shows the layers, in order, with two named profiles as examples. --- A {{term profile}} stacks ordered {{term bundle | bundles}}; patch files then overlay the result, in a fixed order, to build one running dsh plugin tree.

The idea

A running dsh is a plugin tree put together at boot ({{cite docs/architecture.md:15}}). A {{term profile}} is the named composition: it lists the bundles it stacks and keeps the user's own patch file ({{cite docs/architecture.md:17}}). A {{term bundle}} ships Cordis config rows, and the code that mounts them, in a form the layers above it can still change ({{cite docs/architecture.md:19}}). {{link learn/plugins-and-cordis}} already showed that every part of dsh, including a bundle's own code, is a plugin.

An everyday comparison. Think of a profile as a packing list, and each bundle as a sealed box on that list. The boxes stack in a fixed order. A patch file is a note taped on top of the stack. It can replace the whole content of one named box, or add a new box. The comparison stops here. A real note cannot reopen a sealed box, but a patch file can replace a row's whole configuration.

In DeepSeek Harness

The shipped profile templates are plain data. web stacks dsh-base and dsh-web-app; headless stacks dsh-base and dsh-headless ({{cite packages/util/official-bundles/src/bundles.ts:13-18}}). A bundle names its own patch file in its package.json, under a dsh field. The headless bundle points dsh.bundle.patch at ./cordis.patch.yml ({{cite packages/bundle/headless/package.json:39-42}}).

When dsh boots a profile, readProfilePatches() builds the full, ordered patch list. It reads every bundle's own patches first, then the profile's own cordis.patch.yml. Next comes the home-level $DSH_HOME/cordis.patch.yml, then the --patch files from the command line ({{cite packages/boot/app-boot/src/profile-context.ts:75-80}}).

{{link learn/session-and-loop-vocabulary}} names the turn/step vocabulary that the resulting tree runs. {{link concepts/agent-loop-and-session}} reads one of the services this tree mounts.

More detail

composeEntries() applies every layer's patches, in the order above, over an empty entry list ({{cite packages/boot/app-boot/src/profile.ts:755-762}}). A patch names a row by its id: it either replaces that row's whole configuration, or inserts a new row ({{cite docs/architecture.md:25}}). Because later layers apply last, a --patch file can override a setting the home-level patch also touches. The home-level patch can, in turn, override a setting the profile's own cordis.patch.yml sets.

One config knob changes where the home-level patch file is read from: the DSH_HOME environment variable. resolveDshHome() reads it, and falls back to a default path when it is not set ({{cite packages/util/home-paths/src/index.ts:18}}, {{cite packages/util/home-paths/src/index.ts:135-137}}). The --patch <path> flag is repeatable: each use adds one more overlay file, applied in the order given on the command line ({{cite apps/cli/src/args.ts:170}}).

To see the exact tree one invocation mounts, run dsh --profile web --dump-config. Any row it prints can be replaced by a patch of your own ({{cite docs/architecture.md:31-37}}). For the full generated API reference, see the repository's own {{cite docs/subsystems/boot.md}}.

Lowest first: each later layer can still replace or add a row the one above it set.

What can go wrong

A setting that looks wrong may come from a layer you did not check. The home-level $DSH_HOME/cordis.patch.yml outranks the profile's own patch file, and a --patch overlay outranks both ({{cite packages/boot/app-boot/src/profile-context.ts:75-80}}). Run --dump-config to see the composed result instead of reading each file by hand.

This page leaves out presets, hot-module reload of patch files, and platform-gated bundles. It also leaves out how an unreadable or incompatible bundle is skipped instead of failing the boot. Cordis itself is explained only as the framework these bundles and patches build on ({{cite vendor/cordis/}}).

Why it matters. When a plugin seems to be missing, check every patch layer for a disabled: true row with the same id. Do not check only the profile's own patch file.

What does a profile list, and what does a bundle ship?

A profile lists the bundles it stacks ({{cite docs/architecture.md:17}}). A bundle ships Cordis config rows and the code that mounts them ({{cite docs/architecture.md:19}}).

 In which order does dsh apply these: the home-level patch, a bundle's own patch, a --patch overlay, and the profile's own patch file?

A bundle's own patch, then the profile's own cordis.patch.yml, then the home-level patch, then a --patch overlay ({{cite packages/boot/app-boot/src/profile-context.ts:75-80}}).

 Which two bundles does the shipped headless profile stack?

dsh-base and dsh-headless ({{cite packages/util/official-bundles/src/bundles.ts:16-17}}).

 A row id is set by both the home-level patch and a --patch overlay. Which value wins, and why?

The --patch overlay's value. readProfilePatches() appends the --patch overlays after the home-level patch ({{cite packages/boot/app-boot/src/profile-context.ts:75-80}}). composeEntries() then applies every layer's patches over the previous result, in that order ({{cite packages/boot/app-boot/src/profile.ts:755-762}}). The last patch for a row id wins.
