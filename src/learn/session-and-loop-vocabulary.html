The agent loop appends each turn and step boundary to the session log. --- A {{term session}} has {{term turn | turns}}, a turn has {{term step | steps}}, and the agent loop appends each turn or step boundary to the {{term session-log | session log}}.

The idea

A {{term session}} counts its own work with a small, fixed vocabulary ({{cite docs/glossary.md:35-40}}). A {{term turn}} is one drain of admitted input ({{cite docs/glossary.md:37}}). It opens before the first input is claimed, and it closes once nothing is owed ({{cite docs/architecture.md:81}}). A {{term step}} is one model request plus the tool calls its response causes. One turn has zero or more steps ({{cite docs/glossary.md:38}}, {{cite docs/architecture.md:81}}).

An everyday comparison. Think of a turn as one visit to a service counter. It stays open from the moment you are called until the clerk has nothing left to do for you. A step is one question you ask, and the paperwork it causes. The comparison stops here. A real clerk does not keep a permanent, numbered record of each step. The session does: the loop appends a start event and an end event for each step.

The picture

Read panel 2 left to right: the loop opens and closes a turn, and opens and closes each step inside it. It does this by appending one named event for each boundary. The session log on the right keeps every one of them, in order. Panel 1 names the pieces that build the agent this loop belongs to; {{link concepts/agent-loop-and-session}} reads it in detail.

In DeepSeek Harness

The agent loop's turn() method opens a turn by appending a turn/start event before it claims any input ({{cite packages/core/agent-loop/src/agent.ts:334-336}}).

Not every turn spends a step. When the turn's first claim has an empty message list, the loop ends the turn as completed and returns. A listener can make the list empty, for example when it removes the waking message. The loop does not append a step/start event in this case ({{cite packages/core/agent-loop/src/agent.ts:354-361}}).

A {{term round}} sits outside a turn: it is an outer policy iteration, such as a goal round, that contains one turn ({{cite docs/glossary.md:39}}). The goal-round driver reserves at most one next round at a time ({{cite packages/goal/goal-round-driver/src/index.ts:145}}). Each round queues one goal prompt as a user message that carries the round number ({{cite packages/goal/goal-round-driver/src/index.ts:190-195}}). An {{term exchange}} is a run of consecutive turns, from a turn whose first step admits human input until the next such turn ({{cite docs/glossary.md:40}}). The chat client (dsh-client-ui-chat) uses the same grouping: an opening turn starts an exchange ({{cite packages/client/ui-chat/src/client/contract/group-tree.ts:6-7}}). The chat keeps the latest exchange expanded ({{cite docs/glossary.md:40}}).

The loop appends each of these events through one method: Session.append() ({{cite packages/core/session/src/index.ts:806}}). It assigns the event the next sequence number, taken from the log's current length ({{cite packages/core/session/src/index.ts:827-833}}).

{{link concepts/agent-loop-and-session}} reads this same loop and log in more detail, including which object builds the agent that runs it.

More detail

A round's cap is a real config knob, not a fixed number. GoalService declares a defaultMaxGoalRounds setting, with a schema default of 256 ({{cite packages/goal/goal/src/index.ts:239-240}}). A new goal that sets no cap of its own gets this default when it is created ({{cite packages/goal/goal/src/index.ts:211-214}}, {{cite packages/goal/goal/src/index.ts:250-251}}). When a goal reaches its cap, the driver blocks the goal with the code round-limit ({{cite packages/goal/goal-round-driver/src/index.ts:182-187}}). An exchange has no such knob. The glossary defines it only from turn boundaries, and the chat client groups turns from that rule ({{cite docs/glossary.md:40}}).

For the full generated service and event reference, see the repository's own {{cite docs/subsystems/core.md}} and {{cite docs/subsystems/session.md}}.

What can go wrong

Check for a logged step/start event before you assume the model was called. A turn can close as completed with no step at all, only when its first claim has an empty message list ({{cite packages/core/agent-loop/src/agent.ts:356-359}}).

This page only names the words. It leaves out the other reasons a turn can end, such as a blocked input, an error, a cancellation, or a max-tokens limit. {{link concepts/agent-loop-and-session}} covers those.

Why it matters. Code that reads the session log to count an agent's work must use the right unit. Do not count turns when the question is about model calls: count steps instead.

How many steps can one turn have?

Zero or more. A step is one model request plus the tool calls its response causes, and a turn contains zero or more of them ({{cite docs/glossary.md:38}}, {{cite docs/architecture.md:81}}).

 What is the difference between a step and a round?

A step is inside a turn: one model request plus its tool calls. A round is outside a turn: an outer policy iteration, such as a goal round, that contains one turn ({{cite docs/glossary.md:38-39}}).

 Which event does turn() append before it claims the turn's first input?

turn/start. The loop appends it immediately after it computes the turn number, before it claims any input ({{cite packages/core/agent-loop/src/agent.ts:334-336}}).

 A turn's first claim rewrites to an empty message list. Does the loop still log a step/start event?

No. On the turn's first claim, the loop ends that turn as completed and returns. It does not append a step/start event ({{cite packages/core/agent-loop/src/agent.ts:356-359}}).
