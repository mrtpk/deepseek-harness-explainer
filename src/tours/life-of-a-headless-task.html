The idea

The headless bundle is the simplest surface in DeepSeek Harness: no server, no browser, one task in, one answer out. It still uses the same core pieces as every other surface: a {{term profile}}, a {{term plugin | plugin}} tree, an {{term agent | Agent}}, and the {{term session-log | session log}}. This tour has nine stops, in three stages: starting the run, running the task, and finishing the run.

The picture

Read each panel left to right; the three panels run top to bottom in call order. The number on each card matches the stop number below.

Node starts apps/cli/src/bin.ts. Its runCli() function calls parseDshArgs() with the raw argv ({{cite apps/cli/src/bin.ts:29}}). Commander's parser owns only the launcher's own flags: the first token it does not recognize starts the inner arguments, captured by a variadic [args...] positional ({{cite apps/cli/src/args.ts:11-12}}, {{cite apps/cli/src/args.ts:167}}). For dsh --profile headless "task", that leftover is ["task"]: it becomes part of the resolved ProfileInvocation ({{cite apps/cli/src/args.ts:117}}).

Line 35 starts runProfile(). Line 40 passes invocation.args (the ["task"] leftover) straight through.

composeProfile() loads the named profile and resolves any --patch overlays; a profile's own bundle layers and patch files stack in a fixed order ({{cite apps/cli/src/profile-boot.ts:224-236}}, {{cite docs/architecture.md:25}}). runProfile() then calls the shared boot() helper with that composed patch stack, which mounts the resulting plugin tree into one Cordis context ({{cite apps/cli/src/profile-boot.ts:313}}, {{cite apps/cli/src/profile-boot.ts:323}}, {{cite packages/boot/app-boot/src/index.ts:1228}}).

provideCmdline() is what turns the ["task"] leftover into a service other plugins can read ({{cite apps/cli/src/profile-boot.ts:334-338}}).

The dsh-headless bundle's patch inserts two rows. headless-startup injects cmdlineArgs and parses the task positional. headless-runner reads that parsed value back through its own inject ({{cite packages/bundle/headless/cordis.patch.yml:14-26}}).

headless-startup's apply() parses the joined positional words into one task string, then provides it as ctx.headlessStartup ({{cite packages/bundle/headless/src/startup.ts:100}}, {{cite packages/bundle/headless/src/startup.ts:148-155}}).

headless-runner's run() reads the core agents service, then, when no --session-id was given, calls agents.create() with a fresh session id ({{cite packages/bundle/headless/src/index.ts:326}}, {{cite packages/bundle/headless/src/index.ts:388-394}}).

AgentRegistry.create() looks up the one registered factory and delegates construction to it ({{cite packages/core/agent/src/index.ts:416-426}}); {{link concepts/agent-loop-and-session}} explains what that factory builds.

The runner first waits for the new Agent to go idle once, then wraps the task text as a user message and calls agent.followup() ({{cite packages/bundle/headless/src/index.ts:396}}, {{cite packages/bundle/headless/src/index.ts:420-423}}).

followup() queues the message for the next turn and wakes the Agent's driver ({{cite packages/core/agent-loop/src/agent.ts:179-181}}).

Waking the driver starts kick() ({{cite packages/core/agent-loop/src/agent.ts:250}}). kick() calls the private turn() method in a loop, for as long as a turn reports more admitted work ({{cite packages/core/agent-loop/src/agent.ts:268-270}}). Each turn() call opens one turn and runs one or more steps against the model. This tour does not repeat that loop: {{link concepts/agent-loop-and-session}} covers the turn/step mechanism and the session log in detail.

When a step's model response includes tool calls, the loop hands them to the tool service in one batch ({{cite packages/core/agent-loop/src/agent.ts:590-593}}).

Each call runs through three dispatches, in order: tools/pre-execute, tools/execute, tools/post-execute ({{cite packages/core/tools/src/pipeline.ts:199-201}}, {{cite packages/core/tools/src/pipeline.ts:299-301}}, {{cite packages/core/tools/src/pipeline.ts:487-489}}). {{link concepts/tools-and-mcp}} is the page for this pipeline.

After submitting the task, the runner loops: wait for the Agent to go idle, then ask whether any child {{term subagent | subagents}} are still progressing ({{cite packages/bundle/headless/src/index.ts:424-431}}).

waitForChildren() joins any progressing child work and reports whether it had to wait, so the runner knows to check the parent again ({{cite packages/subagent/subagent/src/manager.ts:252-258}}).

Once the wait loop settles, the runner flushes the session's buffered events to durable storage ({{cite packages/bundle/headless/src/index.ts:435}}, {{cite packages/core/session/src/index.ts:1342-1346}}).

Line 437 rereads the log from the task's first sequence number to find the last turn's assistant text ({{cite packages/bundle/headless/src/index.ts:84-111}}). Line 438 writes that text to stdout, and line 443 exits 0 only when the last turn's reason is completed.

More detail

This tour follows the plain-text path: no --json, no --session-id. With --json, the runner projects the run as newline-delimited events instead of final text, through a separate projection object ({{cite packages/bundle/headless/src/index.ts:408-409}}). With --session-id, stop 4 changes: the runner adopts an existing Session instead of creating one ({{cite packages/bundle/headless/src/index.ts:395}}). It rejects an id that is live in this process, carries a preset, or was not recorded for the current working directory ({{cite packages/bundle/headless/src/index.ts:277-287}}, {{cite packages/bundle/headless/src/index.ts:222-242}}).

Two more flags change the run before the task starts. --permission-mode resolves a configured permission preset, and --approval-policy sets the approval behavior after it; both apply before agent.followup() at stop 5 ({{cite packages/bundle/headless/src/index.ts:339-349}}).

For the generated sequence diagram of one turn, and the tool pipeline's full event reference, see the repository's own {{cite docs/agent-lifecycle.md}} and {{cite docs/tool-execution-pipeline.md}}.

The loop at {{cite packages/bundle/headless/src/index.ts:424-431}} does not stop as soon as the Agent looks idle. It stops only when all three of these hold at once:

  1. The Agent's own whenIdle() has resolved for this pass of the loop.
  2. subagents.waitForChildren(agent) returns false: no progressing child work was joined.
  3. The session's sequence number has not grown since whenIdle() resolved (agent.session.seq === idleSeq).

The third check exists for one race. A child agent can settle and wake the parent before the parent's own wait observes it. Re-checking the sequence number catches any new event that arrived in that gap ({{cite packages/bundle/headless/src/index.ts:428}}). Without it, the runner could flush and print one turn too early.

What can go wrong

Check the last turn/end event, not just whether an agent/error fired, before you call a run failed. An agent/error is only treated as this run's failure when no later turn/end commits before stop 9 ({{cite packages/bundle/headless/src/index.ts:411-417}}, {{cite packages/bundle/headless/src/index.ts:436}}).

A flush failure at stop 9 aborts the run before any text reaches stdout. Session.flush() rejects with the first durability-listener failure once every listener has settled ({{cite packages/core/session/src/index.ts:1342-1346}}). The launcher then reports the error on stderr and exits with a non-zero code ({{cite packages/bundle/headless/src/index.ts:308-313}}).

Why it matters. A script that reads a headless run's exit code must not read one agent/error event as a failed run. It must also treat a flush failure as "no durable answer", not as a timeout.

Which file turns the leftover command-line words into the one task string the Agent receives?

packages/bundle/headless/src/startup.ts. Its apply() joins the positional words and provides them as ctx.headlessStartup ({{cite packages/bundle/headless/src/startup.ts:148-155}}).

 Which method actually constructs the new Agent: AgentRegistry.create() or the registered factory?

The registered factory. AgentRegistry.create() only looks up that factory and calls its createAgent() ({{cite packages/core/agent/src/index.ts:416-426}}).

 In what order do the three tool-pipeline events run for one tool call?

tools/pre-execute, then tools/execute, then tools/post-execute ({{cite packages/core/tools/src/pipeline.ts:199-201}}, {{cite packages/core/tools/src/pipeline.ts:299-301}}, {{cite packages/core/tools/src/pipeline.ts:487-489}}).

 The Agent reports idle, but the headless runner does not stop waiting. Name one reason this can happen.

A subagent is still progressing (waitForChildren() returns true), or the session's sequence number grew since the idle check. Either case means a new event arrived in the gap ({{cite packages/bundle/headless/src/index.ts:424-431}}; see the deep dive above).
