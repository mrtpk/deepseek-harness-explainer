The answer is the last assistant text of the {{term agent | Agent}}.

The idea

The headless bundle has no server and no browser: one task goes in, and one answer comes out ({{cite packages/bundle/headless/cordis.patch.yml:1-7}}). It still uses the same core pieces as every other surface: a {{term profile}}, a {{term plugin | plugin}} tree, an {{term agent | Agent}}, and the {{term session-log | session log}}. This tour has nine stops, in three stages: starting the run, running the task, and finishing the run.

The picture

Read each panel left to right; the three panels run top to bottom in call order. The number on each card matches the stop number below.

Node starts apps/cli/src/bin.ts. Its runCli() function calls parseDshArgs() with the raw argv ({{cite apps/cli/src/bin.ts:29}}). The Commander parser reads only the launcher's own flags. The first token that it does not recognize starts the inner arguments, and a variadic [args...] positional captures them ({{cite apps/cli/src/args.ts:4-9}}, {{cite apps/cli/src/args.ts:159-167}}). For dsh --profile headless "task", that leftover is ["task"]: it becomes part of the resolved ProfileInvocation ({{cite apps/cli/src/args.ts:117}}).

Line 35 starts runProfile(). Line 40 passes invocation.args (the ["task"] leftover) straight through.

composeProfile() loads the named profile and reads any --patch overlays ({{cite apps/cli/src/profile-boot.ts:224-236}}). The bundle layers and patch files of a profile stack in a fixed order ({{cite apps/cli/src/profile-boot.ts:211-217}}, {{cite docs/architecture.md:25}}). runProfile() then calls the shared boot() helper with that patch stack ({{cite apps/cli/src/profile-boot.ts:323}}). boot() makes one Cordis context and mounts the plugin tree into it ({{cite packages/boot/app-boot/src/index.ts:1208}}, {{cite packages/boot/app-boot/src/index.ts:1228}}).

provideCmdline() turns the ["task"] leftover into the cmdlineArgs service ({{cite packages/boot/cmdline/src/index.ts:84-88}}). This call runs in the prepare callback of boot(), before the first config-tree entry mounts ({{cite packages/boot/app-boot/src/index.ts:1226-1228}}).

The patch of the dsh-headless bundle inserts two rows ({{cite packages/bundle/headless/cordis.patch.yml:14-26}}). headless-startup injects cmdlineArgs and parses the task positional ({{cite packages/bundle/headless/src/startup.ts:21}}). headless-runner injects headlessStartup and reads its config values from that service ({{cite packages/bundle/headless/cordis.patch.yml:19-25}}).

The apply() function of headless-startup joins the positional words with spaces into one task string ({{cite packages/bundle/headless/src/startup.ts:121-125}}). Then it provides the parsed values as ctx.headlessStartup ({{cite packages/bundle/headless/src/startup.ts:148-155}}).

The run() function of headless-runner reads the core agents service ({{cite packages/bundle/headless/src/index.ts:326}}). When the command line has no --session-id, it calls agents.create() with a new random session id ({{cite packages/bundle/headless/src/index.ts:385}}, {{cite packages/bundle/headless/src/index.ts:388-394}}).

AgentRegistry.create() looks up the registered factory and calls its createAgent() ({{cite packages/core/agent/src/index.ts:416-426}}). {{link concepts/agent-loop-and-session}} explains what that factory builds.

The runner first waits one time for the new Agent to become idle ({{cite packages/bundle/headless/src/index.ts:396}}). Then it puts the task text into a user message and calls agent.followup() ({{cite packages/bundle/headless/src/index.ts:420-423}}).

followup() queues the message for the next turn and wakes the Agent's driver ({{cite packages/core/agent-loop/src/agent.ts:179-181}}).

When the driver wakes, it starts kick() ({{cite packages/core/agent-loop/src/agent.ts:250}}). kick() calls the private turn() method in a loop while turn() returns true ({{cite packages/core/agent-loop/src/agent.ts:268-270}}). Each turn() call opens one turn and runs zero or more steps against the model ({{cite packages/core/agent-loop/src/agent.ts:336}}, {{cite packages/core/agent-loop/src/agent.ts:356-358}}). This tour does not repeat that loop: {{link concepts/agent-loop-and-session}} covers the turn/step mechanism and the session log in detail.

When a step's model response includes tool calls, the loop hands them to the tool service in one batch ({{cite packages/core/agent-loop/src/agent.ts:590-593}}).

A call that passes each stage runs through three waterfalls, in this order: tools/pre-execute, tools/execute, tools/post-execute ({{cite packages/core/tools/src/pipeline.ts:199-201}}, {{cite packages/core/tools/src/pipeline.ts:299-301}}, {{cite packages/core/tools/src/pipeline.ts:487-489}}). {{link concepts/tools-and-mcp}} is the page for this pipeline.

After the runner submits the task, it runs a loop. The loop waits for the Agent to become idle. Then it asks whether child {{term subagent | subagents}} still have work in progress ({{cite packages/bundle/headless/src/index.ts:424-431}}).

waitForChildren() waits for child work in progress. It returns true when it waited, and then the runner must check the parent again ({{cite packages/subagent/subagent/src/manager.ts:247-252}}).

When the wait loop ends, the runner calls sessions.flush() ({{cite packages/bundle/headless/src/index.ts:435}}). SessionStore.flush() sends the buffered events of the session to durable storage ({{cite packages/core/session/src/index.ts:1329-1346}}).

Line 437 reads the log again from the first sequence number of the task ({{cite packages/bundle/headless/src/index.ts:407}}). It keeps the last non-empty assistant text of the interval, and the end reason of the last turn ({{cite packages/bundle/headless/src/index.ts:84-111}}). Line 438 writes that text to stdout. Line 443 requests exit code 0 only when the reason kind is completed, and 1 in all other cases.

More detail

This tour follows the plain-text path: no --json, no --session-id. With --json, a projection object writes the run to stdout as newline-delimited events instead of the final text ({{cite packages/bundle/headless/src/index.ts:408}}, {{cite packages/bundle/headless/src/startup.ts:58}}). With --session-id, stop 4 changes: the runner adopts an existing Session and does not make a new one ({{cite packages/bundle/headless/src/index.ts:395}}). It rejects an id that does not exist, or that is live in this process ({{cite packages/bundle/headless/src/index.ts:277-287}}, {{cite packages/bundle/headless/src/index.ts:297-303}}). It also rejects a session that records an agent preset, a subagent session, and a session from a different working directory ({{cite packages/bundle/headless/src/index.ts:222-242}}).

Other flags change the run before the task starts. --permission-mode selects a configured permission preset. --approval-policy sets the approval behavior after that preset ({{cite packages/bundle/headless/src/index.ts:339-349}}). The runner applies both to the session before agent.followup() at stop 5 ({{cite packages/bundle/headless/src/index.ts:403-406}}). --add-dir adds write roots, and the runner checks that the sandbox-policy row includes them ({{cite packages/bundle/headless/src/index.ts:350-356}}).

For the generated sequence diagram of one turn, and the tool pipeline's full event reference, see the repository's own {{cite docs/agent-lifecycle.md}} and {{cite docs/tool-execution-pipeline.md}}.

The loop at {{cite packages/bundle/headless/src/index.ts:424-431}} does not stop as soon as the Agent looks idle. It stops only when all four of these conditions are true at the same time:

  1. The whenIdle() of the Agent has resolved for this pass of the loop.
  2. subagents.waitForChildren(agent) returns false: it did not wait for child work. When no subagents service is mounted, this check also passes.
  3. The status of the Agent is still idle.
  4. The sequence number of the session has not increased since whenIdle() resolved (agent.session.seq === idleSeq).

The last two checks are for one race. The code comment says that a child can settle and wake the parent before the child wait observes it ({{cite packages/bundle/headless/src/index.ts:428}}). The status check and the sequence check find new parent work that started in that gap ({{cite packages/bundle/headless/src/index.ts:429-430}}). Without them, the runner can flush and print before the new parent turn ends.

What can go wrong

Do not call a run failed only because an agent/error event occurred. Look at the last turn/end event too. The runner records an agent/error of its Agent as a failure. A later turn/end of the same session, at or after the log offset of that error, clears the failure ({{cite packages/bundle/headless/src/index.ts:411-417}}). The runner throws a failure that remains after the flush ({{cite packages/bundle/headless/src/index.ts:436}}).

A flush failure at stop 9 stops the run before the answer goes to stdout. SessionStore.flush() waits for all durability listeners, then throws the first listener failure ({{cite packages/core/session/src/index.ts:1346-1357}}). The apply() function of the runner catches the error from run() ({{cite packages/bundle/headless/src/index.ts:464}}). Then fail() writes the error to stderr and requests exit code 1 ({{cite packages/bundle/headless/src/index.ts:308-313}}).

Why it matters. A script that reads the exit code of a headless run must not treat one agent/error event as a failed run. A flush failure also gives exit code 1, and the events of the run are then possibly not durable.

Which file turns the leftover command-line words into the one task string the Agent receives?

packages/bundle/headless/src/startup.ts. Its apply() joins the positional words into the task string and provides it in ctx.headlessStartup ({{cite packages/bundle/headless/src/startup.ts:121-125}}, {{cite packages/bundle/headless/src/startup.ts:148-155}}).

 Which method actually constructs the new Agent: AgentRegistry.create() or the registered factory?

The registered factory. AgentRegistry.create() only looks up that factory and calls its createAgent() ({{cite packages/core/agent/src/index.ts:422-425}}).

 In what order do the three tool-pipeline events run for one tool call?

tools/pre-execute, then tools/execute, then tools/post-execute ({{cite packages/core/tools/src/pipeline.ts:199-201}}, {{cite packages/core/tools/src/pipeline.ts:299-301}}, {{cite packages/core/tools/src/pipeline.ts:487-489}}).

 The Agent reports idle, but the headless runner does not stop waiting. Name one reason this can happen.

Child work was in progress, so waitForChildren() waited and returned true. Another reason: the Agent became busy again, or the sequence number of the session increased after the idle check ({{cite packages/bundle/headless/src/index.ts:424-431}}; see the deep dive above).
