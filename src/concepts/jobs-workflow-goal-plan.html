The idea

None of these four pieces is part of the turn/step loop itself. A deployment composes each one separately, and the loop runs the same way without it. A background job ({{term job}}) lets a tool keep long work alive while the agent continues. A {{term workflow}} runs a model-written script that starts {{term subagent | subagents}} on the agent's behalf. A {{term goal}} is a durable objective that can trigger its own next round automatically. {{term plan-mode | Plan mode}} only adds guidance text to the model's prompt; it enforces nothing by itself ({{cite docs/subsystems/workflow.md:5}}, {{cite docs/subsystems/plan.md:5}}).

An everyday comparison. Think of a project manager's extra tools beside their own to-do list. One is a tracker board for farmed-out background tasks. Another is a flowchart someone wrote once to run a multi-step project. A third is a standing checklist that queues its own next item until done. The last is a sticky note reminding everyone that the team is only planning for now. The comparison stops here: the note carries no authority, and the manager's own access rules still decide what can happen.

In the code

Step 1: ctx.jobs tracks one producer-owned execution per id

JobRegistry is an abstract seam; a composition loads an implementation such as the in-process dsh-jobs-local ({{cite packages/jobs/jobs/src/index.ts:88-100}}). A job's status is one of running, stopping, completed, killed or failed ({{cite packages/jobs/jobs/src/view.ts:19}}). A job started with an owner session can be read, listed or killed only by that session. Omitting the owner makes the job open to any caller ({{cite packages/jobs/jobs/src/types.ts:179-212}}).

Step 2: a workflow script's agent() calls reach the same subagent seam

ctx.workflowEngine is also an abstract seam, with one engine mounted per context ({{cite packages/workflow/workflow/src/index.ts:157-168}}). The shipped PTC engine parses the script up front, then runs it in a sandboxed Node process under the calling session's file policy ({{cite packages/workflow/workflow-ptc/src/index.ts:103-122}}). Each agent() call the script makes becomes one call to subagents.startActivation(), with delivery: 'caller' so the script can await the result directly ({{cite packages/workflow/workflow-ptc/src/host.ts:200-220}}).

Step 3: a goal drives its own next round, only while armed

GoalService stores one event-sourced goal per session, with phase active, paused, blocked or complete ({{cite docs/subsystems/goal.md:25-30}}). A separate round driver appends the next continuation message, but only when the goal's durable phase is active and its process-local activation is armed ({{cite packages/goal/goal-round-driver/src/index.ts:105-108}}). It also waits until the agent has actually gone idle with no competing message already queued ({{cite packages/goal/goal-round-driver/src/index.ts:111-117}}).

Step 4: plan mode adds a prompt section; it enforces nothing

ctx.planMode logs one replace-whole-value event, plan/mode, and renders a deployment-owned guidance section only while that logged state is active ({{cite docs/subsystems/plan.md:11}}, {{cite docs/subsystems/plan.md:29}}). {{term sandbox | Sandbox mode}} and {{term approval-policy | approval policy}} enforce their own restrictions independently and never read plan state ({{cite docs/subsystems/plan.md:5}}).

More detail

A goal's round cap defaults to 256 and is resolved once, at creation, from the deployment's configured default ({{cite packages/goal/goal/src/index.ts:240}}). Resuming a goal that already reached its cap is rejected outright, with a message naming the exhausted limit, rather than silently resuming it ({{cite packages/goal/goal/src/index.ts:377-381}}). The in-process job provider adds its own defaults on top of the abstract seam. At most 10 concurrent running plus stopping jobs run per owner. It retains 256 KiB of live output per job, and 16 KiB after a job settles ({{cite packages/jobs/jobs-local/src/index.ts:33-40}}).

The workflow engine applies its own ceilings per run: up to 1,000 total agent() calls. Its concurrency limit defaults to min(16, max(1, cores - 2)) when left at 0 ({{cite packages/workflow/workflow-ptc/src/index.ts:106-112}}, {{cite packages/workflow/workflow-ptc/src/index.ts:141-144}}). A script cannot pick its own children's subagent provider. Only a specialized host-side caller may override the engine's configured provider for a run; the script itself never sees that choice ({{cite docs/subsystems/workflow.md:13}}).

A user's plan-mode selection is not committed the instant it is made. It waits as a pending value until the next accepted in-turn pre-step appends it. A selection made after a turn's last such step stays pending until a later turn runs one ({{cite docs/subsystems/plan.md:15}}).

For the full generated references, see the repository's own {{cite docs/subsystems/jobs.md}}, {{cite docs/subsystems/workflow.md}}, {{cite docs/subsystems/goal.md}} and {{cite docs/subsystems/plan.md}}.

What can go wrong

Check activation, not only phase, before expecting an automatic round. A goal stays active in its durable phase even after its process-local activation is disarmed, for example before a driver unloads ({{cite packages/goal/goal/src/index.ts:284-296}}, {{cite packages/goal/goal-round-driver/src/index.ts:105-108}}).

This page leaves out the job output ring's pull-versus-push sources. It also leaves out the workflow engine's parallel()/pipeline() combinators and the browser-facing projections for all four capabilities.

Why it matters. Code that waits for "the goal to keep going" must check the live activation field, not only the durable phase. Otherwise it can wait forever on a goal that is active but disarmed.

Which service lets a tool keep a long-running command active while the agent moves on to other work?

ctx.jobs. It is a seam specifically for long-running producer work tracked outside the turn/step loop ({{cite packages/jobs/jobs/src/index.ts:88-100}}).

 Can a workflow script itself choose which subagent provider its agent() calls use?

No. The engine resolves the provider from its own configuration (or a specialized caller's override); the script "cannot observe or replace either policy" ({{cite docs/subsystems/workflow.md:13}}).

 A goal's phase is active. Does the round driver always queue the next round the moment the agent is idle?

No. It also requires the goal's process-local activation to be armed, and no competing message already queued ({{cite packages/goal/goal-round-driver/src/index.ts:105-108}}, {{cite packages/goal/goal-round-driver/src/index.ts:111-117}}).

 What are the in-process job provider's default per-owner concurrency cap and live output retention?

10 concurrent running/stopping jobs per owner, and 256 KiB of live ring output per job ({{cite packages/jobs/jobs-local/src/index.ts:33-37}}). These are the provider's own defaults, not the abstract seam's.
