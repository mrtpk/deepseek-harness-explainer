The idea

None of these four pieces is part of the turn/step loop itself. A deployment composes each one separately, and the loop runs the same way without it. A background job ({{term job}}) lets a tool keep long work alive while the agent continues. A {{term workflow}} runs a model-written script that starts {{term subagent | subagents}} on the agent's behalf. A {{term goal}} is a durable objective that can start its own next round. {{term plan-mode | Plan mode}} only adds guidance text to the model's prompt. It enforces nothing by itself ({{cite docs/subsystems/workflow.md:5}}, {{cite packages/plan/plan-mode/src/index.ts:1-7}}).

An everyday comparison. Think of a project manager's extra tools beside their own to-do list. One is a tracker board for farmed-out background tasks. Another is a flowchart someone wrote once to run a multi-step project. A third is a standing checklist that adds its own next item until the work is done. The last is a sticky note that tells the team that it only plans for now. The comparison stops here. The note has no authority, and the manager's own access rules still decide what can happen.

The script does not call ctx.subagents directly. The engine host makes the call for the script ({{cite packages/workflow/workflow-ptc/src/host.ts:200-220}}).

In the code

Step 1: ctx.jobs tracks one producer-owned execution per id

JobRegistry is an abstract seam. A composition loads an implementation such as the in-process dsh-jobs-local ({{cite packages/jobs/jobs/src/index.ts:88-96}}). A job's status is one of running, stopping, completed, killed or failed ({{cite packages/jobs/jobs/src/view.ts:19}}). Only the owner session can read, list or kill a job that has an owner. A job without an owner is open to all callers ({{cite packages/jobs/jobs/src/types.ts:184-190}}, {{cite packages/jobs/jobs-local/src/index.ts:310-314}}, {{cite packages/jobs/jobs-local/src/index.ts:405-414}}).

Step 2: a workflow script's agent() calls reach the same subagent seam

ctx.workflowEngine is also an abstract seam, with one engine per context ({{cite packages/workflow/workflow/src/index.ts:157-168}}, {{cite docs/subsystems/workflow.md:5}}). The shipped PTC engine parses the script first. Then it runs the script in a sandboxed Node process under the calling session's file policy ({{cite packages/workflow/workflow-ptc/src/index.ts:3}}, {{cite packages/workflow/workflow-ptc/src/index.ts:134-137}}, {{cite packages/workflow/workflow-ptc/src/index.ts:167}}). Each agent() call in the script becomes one call to subagents.startActivation(). The call uses delivery: 'caller', so the engine gets the child's result back ({{cite packages/workflow/workflow-ptc/src/host.ts:200-220}}).

Step 3: a goal drives its own next round, only while armed

GoalService keeps the current goal of a session in that session's log ({{cite packages/goal/goal/src/index.ts:235-236}}). The goal phase is active, paused, blocked or complete ({{cite docs/subsystems/goal.md:24-30}}). A separate round driver starts the next round only when the durable phase is active and the process-local activation is armed ({{cite packages/goal/goal-round-driver/src/index.ts:105-108}}). The agent must also be idle, with no competing message in the queue ({{cite packages/goal/goal-round-driver/src/index.ts:111-117}}).

Step 4: plan mode adds a prompt section; it enforces nothing

ctx.planMode logs one whole-value event, plan/mode ({{cite packages/plan/plan-mode/src/index.ts:48-53}}). It adds a deployment-owned guidance section, plan:policy, only while the selected state is active. The selected state is a pending user selection, or else the logged state ({{cite packages/plan/plan-mode/src/index.ts:197-204}}, {{cite packages/plan/plan-mode/src/index.ts:382-384}}). {{term sandbox | Sandbox mode}} and {{term approval-policy | approval policy}} enforce their own restrictions and do not read plan state ({{cite packages/plan/plan-mode/src/index.ts:5-7}}).

More detail

A goal's round cap comes from the create request. When the request has no cap, the deployment default applies, and that default is 256 ({{cite packages/goal/goal/src/index.ts:211-214}}, {{cite packages/goal/goal/src/index.ts:240}}). A later edit can change the cap ({{cite packages/goal/goal/src/index.ts:342}}). A resume of a goal that used all its rounds fails with an error that names the limit ({{cite packages/goal/goal/src/index.ts:377-381}}). The in-process job provider adds its own defaults on top of the abstract seam. At most 10 running plus stopping jobs can exist per owner, or in the shared bucket for jobs without an owner ({{cite packages/jobs/jobs-local/src/index.ts:47-51}}). It keeps 256 KiB of live output per job. After a job settles, it keeps 16 KiB plus the bytes that the model did not read yet ({{cite packages/jobs/jobs-local/src/index.ts:33-40}}, {{cite packages/jobs/jobs-local/src/index.ts:54-58}}).

The workflow engine has its own limits for each run. The default limit is 1,000 agent() calls in total. The concurrency limit is min(16, max(1, cores - 2)) when the config leaves it at 0, which is the default ({{cite packages/workflow/workflow-ptc/src/index.ts:106-112}}, {{cite packages/workflow/workflow-ptc/src/index.ts:141-144}}). The subagent provider for the children comes from the engine config (default spawn). Only a specialized host-side caller can override it for a run. The script cannot see or change that choice ({{cite packages/workflow/workflow-ptc/src/index.ts:107}}, {{cite packages/workflow/workflow-ptc/src/index.ts:137}}, {{cite docs/subsystems/workflow.md:13}}). An agent() call can still ask for a model provider and a model for its child ({{cite packages/workflow/workflow-ptc/src/host.ts:213-218}}).

The service does not log a user's plan-mode selection immediately. The selection stays pending until the next accepted in-turn pre-step appends it. A selection made after the last such step of a turn stays pending until a later turn ({{cite packages/plan/plan-mode/src/index.ts:209-228}}, {{cite docs/subsystems/plan.md:15}}).

For the full generated references, see the repository's own {{cite docs/subsystems/jobs.md}}, {{cite docs/subsystems/workflow.md}}, {{cite docs/subsystems/goal.md}} and {{cite docs/subsystems/plan.md}}.

What can go wrong

Check activation and phase before you wait for an automatic round. A goal stays active in its durable phase after its process-local activation is disarmed, for example before a driver unloads ({{cite packages/goal/goal/src/index.ts:284-296}}, {{cite packages/goal/goal-round-driver/src/index.ts:105-108}}).

This page leaves out the job output ring's pull-versus-push sources. It also leaves out the workflow engine's parallel()/pipeline() combinators and the browser-facing projections for all four capabilities.

Why it matters. Code that waits for the next goal round must check the live activation field and the durable phase. If it checks only the phase, it can wait for a round that the driver does not start ({{cite packages/goal/goal-round-driver/src/index.ts:105-108}}).

Which service lets a tool keep a long-running command active while the agent moves on to other work?

ctx.jobs. The JobRegistry seam registers as ctx.jobs. It tracks long producer work, such as a bash command, outside the turn/step loop ({{cite packages/jobs/jobs/src/index.ts:88-96}}, {{cite packages/jobs/jobs/src/types.ts:179-183}}).

 Can a workflow script itself choose which subagent provider its agent() calls use?

No. The engine gets the subagent provider from its own configuration, or from a specialized caller's override. The script "cannot observe or replace either policy" ({{cite packages/workflow/workflow-ptc/src/index.ts:137}}, {{cite docs/subsystems/workflow.md:13}}).

 A goal's phase is active. Does the round driver always start the next round when the agent is idle?

No. The goal's process-local activation must also be armed, and no competing message can be in the queue ({{cite packages/goal/goal-round-driver/src/index.ts:105-108}}, {{cite packages/goal/goal-round-driver/src/index.ts:111-117}}).

 What are the in-process job provider's default per-owner concurrency cap and live output retention?

10 running or stopping jobs per owner, and 256 KiB of live ring output per job ({{cite packages/jobs/jobs-local/src/index.ts:33-37}}). These are the provider's own defaults. The abstract seam does not set them.
