The idea

{{term approval-policy | Approval}} answers one question at the moment a tool wants to act: may this specific action proceed ({{cite docs/subsystems/approval.md:5}})? {{link concepts/sandbox-and-execution | Sandbox mode}} is different. It sets the file effects of all calls under a mode before the calls run. Approval decides one call, once, and it asks composed answerers for the decision. ctx.approval owns the full exchange. It logs the ask, asks the answerers, logs the outcome, and returns the outcome to the caller ({{cite packages/interaction/user-approval/src/index.ts:242-261}}).

An everyday comparison. Think of a doorman who approves the entry of one visitor now. A building policy, in contrast, applies to all visitors before they arrive. The comparison stops here. The approval question does not copy the tool arguments. It can name the tool call that the user already sees, through an optional callId ({{cite packages/interaction/user-approval/src/index.ts:124-141}}).

The picture

Read panel 1 from left to right. In the tool pipeline, a decision of kind ask is the trigger. The audit and the decision occur inside ctx.approval. Read panel 2 as two policies. "never" decides before an answerer runs. "ask" gives the request to the composed answerers in registration order.

In the code

Step 1: a kind-ask decision reaches ctx.approval.request()

A tools/pre-execute listener, such as a hook, can return { kind: 'ask' } instead of an allow or a deny ({{cite packages/core/tools/src/events.ts:18}}, {{cite packages/core/tools/src/contracts.ts:357-361}}). The tool pipeline then calls ctx.approval.request() and maps the outcome back. Only allowed-once proceeds. The other three outcomes each deny with their own reason ({{cite packages/core/tools/src/pipeline.ts:449-471}}). When the deployment has no approval service, or the call has no agent, the pipeline denies the call ({{cite packages/core/tools/src/pipeline.ts:436-448}}).

Step 2: the session's policy decides before any answerer runs

Inside request(), decide() checks the session's effective policy first. A 'never' policy returns rejected before the answerer waterfall starts ({{cite packages/interaction/user-approval/src/index.ts:293-318}}). The service itself does this check. Thus an answerer added later with prepend cannot bypass it ({{cite packages/interaction/user-approval/src/index.ts:296-301}}).

Step 3: one answerer claims the request, or passes it on

An 'ask' policy runs a {{term typed-event | waterfall}} of composed answerers for the agent, in registration order ({{cite packages/interaction/user-approval/src/index.ts:306-310}}, {{cite docs/cordis-primer.md:22}}). An answerer that does not own the agent calls next(). When no answerer claims the ask, the result is unavailable ({{cite packages/interaction/user-approval/src/index.ts:309}}). The ACP automation bridge is one example. It sends a session/request_permission call to its connected client ({{cite packages/acp/acp/src/index.ts:158-176}}).

More detail

The default policy is 'ask'. A deployment can set 'never' for unattended or CI use ({{cite packages/interaction/user-approval/src/index.ts:153-159}}, {{cite packages/interaction/user-approval/src/index.ts:170-172}}). A session can override the policy at runtime. setPolicy() appends the new approval/policy event. Then it injects a user message that tells the model about the switch ({{cite packages/interaction/user-approval/src/index.ts:211-222}}). allowed-once is a one-shot grant for one ask ({{cite packages/interaction/user-approval/src/types.ts:28-32}}). The service keeps no grant for later calls ({{cite packages/interaction/user-approval/src/index.ts:242-261}}).

The same seam decides a {{term sandbox-escalation | sandbox escalation}}, the retry that {{link concepts/sandbox-and-execution | the sandbox page}} describes. After a sandbox denial, a tool can ask for one retry under a strictly wider mode. The tool sends that ask through ctx.approval.request() ({{cite packages/sandbox/sandbox/src/escalation.ts:1-14}}). This page covers the general approval decision. The sandbox page tells what "strictly wider" means.

For the full generated service and event reference, see the repository's own {{cite docs/subsystems/approval.md}}.

A tool call does not see the raw return value of an answerer. It sees one of four normalized outcomes ({{cite packages/interaction/user-approval/src/types.ts:28-32}}, {{cite packages/interaction/user-approval/src/index.ts:311-318}}):

What can go wrong

Call ctx.approval.request() only inside an open turn of the requesting session. Outside a turn, it throws an Error and returns no decision. The audit pair must stay inside the turn boundary of the durable log ({{cite packages/interaction/user-approval/src/index.ts:242-250}}).

This page leaves out cancellation races against a live signal, scope-filtered dispatch to the right agent, and the SDK's own opt-in approval/request bridge.

Why it matters. A missing or throwing answerer does not grant an action. The service changes the result to unavailable ({{cite packages/interaction/user-approval/src/index.ts:306-318}}). The tool pipeline and the sandbox escalation deny on each outcome except allowed-once ({{cite packages/core/tools/src/pipeline.ts:457-471}}, {{cite docs/subsystems/approval.md:5}}). The service fails closed, so a caller cannot forget this check.

What are the four closed outcomes ctx.approval.request() can return?

allowed-once, rejected, cancelled, and unavailable ({{cite packages/interaction/user-approval/src/types.ts:28-32}}). Only allowed-once is a grant.

 A session's approval policy is 'never'. Does any composed answerer see the request?

No. decide() returns rejected before the answerer waterfall starts, so no answerer gets the ask ({{cite packages/interaction/user-approval/src/index.ts:301}}).

 How does approval differ from sandbox mode?

Sandbox mode sets the file effects of all calls under a mode before the calls run ({{link concepts/sandbox-and-execution}}). Approval decides one specific action, once, at the time of the ask ({{cite docs/subsystems/approval.md:5}}).

 A composed answerer throws an exception while deciding. What outcome does request() return, and what does the tool pipeline do with it?

unavailable. The service changes a throw to the fail-closed outcome ({{cite packages/interaction/user-approval/src/index.ts:315-317}}). The tool pipeline then denies the call with "no approval channel is available" ({{cite packages/core/tools/src/pipeline.ts:467-470}}).
