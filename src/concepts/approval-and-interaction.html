The idea

{{term approval-policy | Approval}} answers one question at the moment a tool wants to act: may this specific action proceed ({{cite docs/subsystems/approval.md:5}})? This differs from {{link concepts/sandbox-and-execution | sandbox mode}}, which fixes a whole mode's file effects ahead of time for every call under it. Approval decides one call, once, by asking composed answerers for a decision. ctx.approval owns the whole exchange: it logs the ask, asks the answerers, logs the outcome, and returns it to the caller ({{cite packages/interaction/user-approval/src/index.ts:242-261}}).

An everyday comparison. Think of a doorman who approves one visitor's entry right now, instead of a building policy fixed for everyone in advance. The comparison stops here: the doorman's question never even describes what the visitor carries. It only names the already-presented tool call, so an answerer's decision attaches to arguments that cannot drift from what the model actually asked for ({{cite packages/interaction/user-approval/src/index.ts:124-128}}).

The picture

Read panel 1 left to right: the tool's own kind-ask decision is the only trigger; everything else happens inside ctx.approval. Read panel 2 as two policies: "never" decides before any answerer runs, while "ask" lets composed answerers compete in registration order.

In the code

Step 1: a tool's kind-ask decision reaches ctx.approval.request()

A tool's pre-execute check can return { kind: 'ask' } instead of an outright allow or deny ({{cite packages/core/tools/src/contracts.ts:357-361}}). The tool pipeline then calls ctx.approval.request() and maps its outcome straight back. Only allowed-once proceeds; the other three outcomes each deny with their own reason ({{cite packages/core/tools/src/pipeline.ts:449-471}}).

Step 2: the session's policy decides before any answerer runs

Inside request(), decide() checks the session's effective policy first. A 'never' policy returns rejected deterministically, before the answerer waterfall ever dispatches ({{cite packages/interaction/user-approval/src/index.ts:293-318}}). This check runs inside the service itself, so an answerer composed later with prepend still cannot bypass it.

Step 3: one answerer claims the request, or passes it on

An 'ask' policy runs a {{term typed-event | waterfall}} of composed answerers for the agent, in registration order ({{cite docs/cordis-primer.md:22}}). The ACP automation bridge is one example: it turns the request into a session/request_permission call to its connected client ({{cite packages/acp/acp/src/index.ts:158-176}}).

More detail

The default policy is 'ask'; a deployment can configure 'never' instead for an unattended or CI stance ({{cite packages/interaction/user-approval/src/index.ts:170-172}}). A session can override this at runtime. setPolicy() appends the new approval/policy event, then injects a user-visible message so the model learns of the switch ({{cite packages/interaction/user-approval/src/index.ts:211-222}}). Nothing is pre-approved across calls; a grant from one allowed-once outcome never covers a later, different action.

The same seam decides a {{term sandbox-escalation | sandbox escalation}}, the retry described on {{link concepts/sandbox-and-execution | the sandbox page}}. A call denied under one mode can route one strictly-wider retry through this exact ctx.approval.request() path. This page covers the general approval decision; the sandbox page covers what "strictly wider" means.

For the full generated service and event reference, see the repository's own {{cite docs/subsystems/approval.md}}.

What can go wrong

Calling ctx.approval.request() with no open turn on the requesting session throws an Error at once; it does not return a decision. The audit pair must stay inside the durable log's turn boundary ({{cite packages/interaction/user-approval/src/index.ts:242-250}}).

This page leaves out cancellation races against a live signal, scope-filtered dispatch to the right agent, and the SDK's own opt-in approval/request bridge.

Why it matters. A missing or throwing answerer never silently grants an action; it normalizes to unavailable, which every caller treats as a deny ({{cite packages/interaction/user-approval/src/index.ts:306-318}}). The seam is fail-closed by construction, not by each caller remembering to check.

What are the four closed outcomes ctx.approval.request() can return?

allowed-once, rejected, cancelled, and unavailable ({{cite packages/interaction/user-approval/src/types.ts:28-32}}). Only allowed-once is a grant.

 A session's approval policy is 'never'. Does any composed answerer see the request?

No. decide() returns rejected deterministically before the answerer waterfall dispatches, so no answerer is ever asked ({{cite packages/interaction/user-approval/src/index.ts:301}}).

 How does approval differ from sandbox mode?

Sandbox mode fixes a whole mode's file effects ahead of time for every call under it ({{link concepts/sandbox-and-execution}}). Approval decides one specific action, once, at the moment it is asked ({{cite docs/subsystems/approval.md:5}}).

 A composed answerer throws an exception while deciding. What outcome does request() return, and what does the tool pipeline do with it?

unavailable: a throwing answerer is normalized to the fail-closed outcome ({{cite packages/interaction/user-approval/src/index.ts:317}}). The tool pipeline then denies the call with "no approval channel is available" ({{cite packages/core/tools/src/pipeline.ts:467-470}}).
