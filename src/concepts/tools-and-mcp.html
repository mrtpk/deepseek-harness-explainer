The idea

ctx.tools is the tool registry. A first-party plugin registers a tool directly ({{cite packages/core/tools/src/index.ts:128}}). An {{term mcp | MCP}} server's tools arrive the same way. The MCP client is one plugin per configured server ({{cite docs/subsystems/mcp.md:41}}). It lists the server's tools, then registers each one into the same registry. Each registered name starts with mcp__ and the server's name ({{cite packages/mcp/mcp-client/src/tools.ts:150}}, {{cite packages/mcp/mcp-client/src/tools.ts:82}}). Whatever the source, a {{term tool-call | tool call}} then runs through the same fixed pipeline: tools/pre-execute, then tools/execute, then tools/post-execute ({{cite docs/architecture.md:99}}).

An everyday comparison. Think of airport customs. Pre-execute is the passport check: allow, deny, or send the traveller to a human officer. Execute is the crossing. Post-execute is the declaration review on the other side: accept the bag's contents, or send some of it back. The comparison stops here. No later listener can reverse a guard's denial. Post-execute examines the result of the call, not a person.

In the code

Step 1: registration, from a first-party plugin or an MCP client

ctx.tools.register(definition) is the one entry point. A scoped registration shadows a global tool with the same name ({{cite packages/core/tools/src/index.ts:121-123}}). No plugin can register the reserved run_code name ({{cite packages/core/tools/src/index.ts:145-147}}). An MCP client calls the same method once per discovered tool ({{cite packages/mcp/mcp-client/src/tools.ts:149-151}}). First, it makes a public name of the form mcp__<serverName>__<rawName> ({{cite packages/mcp/mcp-client/src/tools.ts:81-82}}).

Step 2: the fixed pipeline order

One call's scheduler runs these five actions in order ({{cite docs/architecture.md:99}}):

  1. It logs tool/call ({{cite packages/core/tools/src/batch.ts:157}}). It logs only when the batch belongs to a model step ({{cite packages/core/tools/src/batch.ts:243-244}}).
  2. prepare() runs the tools/pre-execute waterfall ({{cite packages/core/tools/src/batch.ts:159}}).
  3. dispatch() runs the tools/execute waterfall ({{cite packages/core/tools/src/batch.ts:163}}).
  4. complete() runs the tools/post-execute waterfall ({{cite packages/core/tools/src/batch.ts:144}}). It skips the waterfall for a final-result outcome, for example when a pre-execute listener throws ({{cite packages/core/tools/src/pipeline.ts:337-341}}, {{cite packages/core/tools/src/pipeline.ts:230-231}}).
  5. It logs tool/result ({{cite packages/core/tools/src/batch.ts:146}}).

Step 3: pre-execute decides allow, deny, cancel, or ask

The tools/pre-execute waterfall returns one of four decisions ({{cite packages/core/tools/src/contracts.ts:357-361}}). If the decision is allow, the registry then runs the registered guards ({{cite packages/core/tools/src/pipeline.ts:213}}). The first guard that returns a reason denies the call ({{cite packages/core/tools/src/index.ts:393-401}}). A guard has no allow result, so it cannot clear a denial ({{cite packages/core/tools/src/contracts.ts:383-391}}). A denied or cancelled call skips tools/execute, but it still goes to tools/post-execute ({{cite packages/core/tools/src/pipeline.ts:210-225}}).

Step 4: post-execute can accept, replace, or block the result

The tools/post-execute waterfall returns accept or block ({{cite packages/core/tools/src/contracts.ts:367-370}}). An accept can replace the content or the success value. A block changes the result into an error result. One decision cannot replace both content and value ({{cite packages/core/tools/src/pipeline.ts:501-502}}).

More detail

The names are different on purpose. tool/call and tool/result (singular) are durable SessionEvents. In a model step, the scheduler appends each one once per call, before and after the pipeline ({{cite packages/core/tools/src/batch.ts:247}}, {{cite packages/core/tools/src/batch.ts:256}}). Without a model step, it appends neither ({{cite packages/core/tools/src/executor.ts:39-43}}). tools/pre-execute, tools/execute and tools/post-execute (plural) are live Cordis waterfalls on the ToolsService. Any plugin can join one. An agent-scoped listener gets the calls of its own scope and of the scopes under it, but not the calls of other agents ({{cite packages/core/scope/src/index.ts:170-181}}).

{{term mcp | MCP}} resources do not have a separate path. The mcpResources service registers three shared tools: list_mcp_resources, list_mcp_resource_templates and read_mcp_resource ({{cite packages/mcp/mcp-resources/src/tools.ts:31-60}}). A resource read is thus a usual tool call through the pipeline above. A server's nonblank instructions also go into the system prompt as their own section ({{cite docs/subsystems/mcp.md:67}}, {{cite packages/mcp/mcp-client/src/server-context.ts:32-38}}).

For the full generated service and type reference, see the repository's own {{cite docs/subsystems/tools.md}} and {{cite docs/subsystems/mcp.md}}.

What can go wrong

A call to a name the registry cannot resolve throws ToolNotFoundError, the same as a tool body that throws. The same catch changes each one into an error result ({{cite packages/core/tools/src/pipeline.ts:272-281}}). Thus both still go to tools/post-execute ({{cite packages/core/tools/src/pipeline.ts:316-321}}).

This page leaves out approval ("ask") prompts, exclusive-versus-parallel call scheduling, and MCP's own protocol negotiation and reconnection behaviour.

Why it matters. To stop a call, use a guard or a tools/pre-execute listener. Do not let the tool body throw for this purpose. A thrown error still gives a result that the model sees.

In which order does one tool call run through the pipeline?

tool/call is logged, then tools/pre-execute, then tools/execute, then tools/post-execute, then tool/result is logged ({{cite docs/architecture.md:99}}, {{cite packages/core/tools/src/batch.ts:157-163}}, {{cite packages/core/tools/src/batch.ts:144-146}}).

 How does an MCP server's tool get a unique name in the registry?

The client makes the public name mcp__<serverName>__<rawName>. Thus the same tool name from two servers gives two different names. If the client must change or cut the name, it adds a hash of the server name and the tool name ({{cite packages/mcp/mcp-client/src/tools.ts:81-87}}).

 What is the difference between tool/call and tools/pre-execute?

tool/call (singular) is a durable session event logged once. tools/pre-execute (plural) is a live waterfall that plugins can join to allow, deny, cancel, or ask about the call ({{cite packages/core/tools/src/batch.ts:247}}, {{cite packages/core/tools/src/pipeline.ts:199-202}}).

 A tools/pre-execute listener allows a call, but a registered guard then denies it. Can a later listener undo that denial?

No. Guards run after all tools/pre-execute listeners are complete. A guard can only add a denial reason. It has no "allow" result. Thus no listener order can change a guard's denial back into permission ({{cite packages/core/tools/src/pipeline.ts:199-213}}, {{cite packages/core/tools/src/contracts.ts:383-391}}).
