The idea

ctx.tools is the tool registry. A first-party plugin registers a tool directly ({{cite packages/core/tools/src/index.ts:128}}). An {{term mcp | MCP}} server's tools arrive the same way. One client plugin per configured server lists the server's tools, then registers each one into the same registry. Each registered name carries the server's own name ({{cite packages/mcp/mcp-client/src/tools.ts:150}}, {{cite packages/mcp/mcp-client/src/tools.ts:82}}). Whatever the source, every {{term tool-call | tool call}} then runs through the same fixed pipeline: tools/pre-execute, then tools/execute, then tools/post-execute ({{cite docs/architecture.md:99}}).

An everyday comparison. Think of airport customs. Pre-execute is the passport check: allow, deny, or send the traveller to a human officer. Execute is the actual crossing. Post-execute is the declaration review on the other side: accept the bag's contents, or send some of it back. The comparison stops here. A pre-execute guard's denial cannot be reversed by a later listener, just like a customs officer's decision. Post-execute's accept or block, though, looks at the dispatched result, not at a person.

In the code

Step 1: registration, from a first-party plugin or an MCP client

ctx.tools.register(definition) is the one entry point. A scoped registration shadows a global tool with the same name. The reserved run_code name cannot be taken ({{cite packages/core/tools/src/index.ts:128-153}}). An MCP client calls the same method once per discovered tool, after it builds a public name of the form mcp__<serverName>__<rawName> ({{cite packages/mcp/mcp-client/src/tools.ts:81-82}}, {{cite packages/mcp/mcp-client/src/tools.ts:150}}).

Step 2: the fixed pipeline order, confirmed at every call site

One call's scheduler runs these five actions in order ({{cite docs/architecture.md:99}}):

  1. It logs tool/call ({{cite packages/core/tools/src/batch.ts:157}}).
  2. prepare() runs the tools/pre-execute waterfall ({{cite packages/core/tools/src/batch.ts:159}}).
  3. dispatch() runs the tools/execute waterfall ({{cite packages/core/tools/src/batch.ts:163}}).
  4. complete() runs the tools/post-execute waterfall ({{cite packages/core/tools/src/batch.ts:144}}).
  5. It logs tool/result ({{cite packages/core/tools/src/batch.ts:146}}).

Step 3: pre-execute decides allow, deny, cancel, or ask

The tools/pre-execute waterfall returns one of four decisions ({{cite packages/core/tools/src/contracts.ts:357-361}}). Right after, every registered guard gets one more look at the call. A guard can only add a denial reason; it can never clear one a listener already returned ({{cite packages/core/tools/src/pipeline.ts:213}}, {{cite packages/core/tools/src/contracts.ts:391}}).

Step 4: post-execute can accept, replace, or block the result

The tools/post-execute waterfall returns accept (optionally replacing content or the success value) or block (turning the result into an error) ({{cite packages/core/tools/src/contracts.ts:367-370}}). A listener may replace content or a value, never both in the same decision ({{cite packages/core/tools/src/pipeline.ts:501-502}}).

More detail

The names split on purpose. tool/call and tool/result (singular) are durable SessionEvents, appended once each, before and after the pipeline runs ({{cite packages/core/tools/src/batch.ts:247}}, {{cite packages/core/tools/src/batch.ts:256}}). tools/pre-execute, tools/execute and tools/post-execute (plural) are live Cordis waterfalls on the scoped ToolsService. Any plugin can join one. An agent-scoped listener only sees that agent's calls ({{cite docs/architecture.md:99}}).

{{term mcp | MCP}} resource access is a separate, read-only path. A connected server's resources are listed and read through ctx.mcpResources, not through the tool pipeline above. A server's nonblank instructions, though, still join the system prompt as their own section ({{cite docs/subsystems/mcp.md:67}}).

For the full generated service and type reference, see the repository's own {{cite docs/subsystems/tools.md}} and {{cite docs/subsystems/mcp.md}}.

What can go wrong

A call to a name the registry cannot resolve throws ToolNotFoundError, exactly like a throwing tool body. The same surrounding catch turns either one into a structured error result. Both therefore still reach tools/post-execute, instead of skipping it ({{cite packages/core/tools/src/pipeline.ts:272-281}}).

This page leaves out approval ("ask") prompts, exclusive-versus-parallel call scheduling, and MCP's own protocol negotiation and reconnection behaviour.

Why it matters. A plugin that must veto a call should use a guard or tools/pre-execute. It should not rely on the tool itself throwing. A thrown error still produces a model-visible result, not a skipped call.

In which order does one tool call run through the pipeline?

tool/call is logged, then tools/pre-execute, then tools/execute, then tools/post-execute, then tool/result is logged ({{cite docs/architecture.md:99}}, {{cite packages/core/tools/src/batch.ts:157-163}}).

 How does an MCP server's tool get a unique name in the registry?

Its public name is built as mcp__<serverName>__<rawName>, so the same tool name from two servers stays distinct ({{cite packages/mcp/mcp-client/src/tools.ts:81-82}}).

 What is the difference between tool/call and tools/pre-execute?

tool/call (singular) is a durable session event logged once. tools/pre-execute (plural) is a live waterfall plugins can join to allow, deny, cancel, or ask about the call ({{cite packages/core/tools/src/batch.ts:247}}, {{cite packages/core/tools/src/pipeline.ts:200}}).

 A tools/pre-execute listener allows a call, but a registered guard then denies it. Can a later listener undo that denial?

No. Guards run after every tools/pre-execute listener and can only add a denial reason. They have no "allow" return. Listener order therefore cannot turn a guard's denial back into permission ({{cite packages/core/tools/src/pipeline.ts:213}}, {{cite packages/core/tools/src/contracts.ts:391}}).
