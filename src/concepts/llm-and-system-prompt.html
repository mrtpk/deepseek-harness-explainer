The idea

The agent loop sends each model call through one service: ctx.llm. ctx.llm does not talk to a provider itself. An object called a {{term provider-adapter | provider adapter}} does that work. ctx.llm selects the adapter registered for the request's provider name ({{cite packages/llm/llm/src/index.ts:401}}, {{cite packages/llm/llm/src/index.ts:1167}}).

Before the loop calls ctx.llm, it builds that request's {{term system-prompt | system prompt}}. Plugins register ordered sections with ctx.systemPrompt. One assembly call collects them for the current step, and renderPrompt() makes the text ({{cite packages/core/agent-loop/src/agent.ts:294}}, {{cite packages/core/agent-loop/src/agent.ts:442}}).

An everyday comparison. Think of ctx.llm as a phone switchboard. You dial a provider's name, and the switchboard connects you to the one line registered for it. The system prompt is a briefing note read onto the call first. The comparison stops here. A real briefing note does not change between calls. The system prompt can change, because a section's text can be a function of the current step ({{cite packages/core/system-prompt/src/index.ts:61-66}}).

In the code

Step 1: ctx.llm routes stream() to the adapter registered for one provider name

A provider adapter extends the abstract LlmAdapter class. A plugin registers it with ctx.llm.registerAdapter(providers, adapter) ({{cite packages/llm/llm/src/index.ts:401}}). DeepSeekAdapter is one such adapter ({{cite packages/llm/llm-deepseek/src/adapter.ts:22}}). The DeepSeek host code registers it for one provider name ({{cite packages/llm/llm-deepseek/src/host.ts:81}}).

Step 2: the agent assembles the system prompt before it builds the request

Each step's preStep() calls ctx.systemPrompt.assemble() with the step's model selection and the tools admitted for that step ({{cite packages/core/agent-loop/src/agent.ts:288-294}}). renderPrompt() then changes that assembly into plain text ({{cite packages/core/agent-loop/src/agent.ts:442}}).

Step 3: the rendered prompt is committed to the session, not sent as a hidden field

systemPrompt.project(renderedPrompt, ...) finds what changed since the last step. The loop appends each resulting commit as a system/message session event ({{cite packages/core/agent-loop/src/agent.ts:453-461}}). If nothing changed, there is no commit ({{cite packages/core/agent-loop/src/runtime-context.ts:103-106}}). The system prompt reaches the model as logged history, not as a field only the request carries ({{cite docs/architecture.md:112}}).

Step 4: buildRequest() derives the history and streams the frozen request

buildRequest() logs a request/header in three cases. The cases are the first step of this loop instance, a header change (config or tools), and a new request series ({{cite packages/core/agent-loop/src/agent.ts:675-691}}). Then it makes the model-visible message list from the session log with session.deriveMessages() ({{cite packages/core/agent-loop/src/agent.ts:728}}). Before this, prepareRequest() got a prepared call from ctx.llm.prepareCall() ({{cite packages/core/agent-loop/src/agent.ts:644}}). The step streams the frozen request through that prepared call. If no adapter is registered for the provider, it uses ctx.llm.stream() ({{cite packages/core/agent-loop/src/agent.ts:646-650}}, {{cite packages/core/agent-loop/src/agent.ts:490}}).

More detail

registerAdapter() takes every provider name an adapter owns and registers them together, all at once. If one of those names already has an adapter, the call fails with DUPLICATE_ADAPTER and no name is registered ({{cite packages/llm/llm/src/index.ts:393-396}}, {{cite packages/llm/llm/src/index.ts:437-444}}). Both ctx.llm.stream() and a prepared call's stream() run inside the llm/stream waterfall ({{cite packages/llm/llm/src/index.ts:1010}}, {{cite packages/llm/llm/src/index.ts:1170-1183}}). Thus a plugin can wrap each call, for example for retry, before the call gets to the adapter.

A prompt section's order sets the position of its text. Sections join in ascending order, and equal orders use name order ({{cite packages/core/system-prompt/src/index.ts:56-60}}). A duplicate section name in one layer throws, and so does an order that is not finite ({{cite packages/core/system-prompt/src/index.ts:477-493}}). A section can also set complete. Assembly still runs its full waterfall, but then keeps that one section as the whole prompt. Two active complete sections make assembly fail ({{cite packages/core/system-prompt/src/index.ts:69-75}}).

For the full generated service and type reference, see the repository's own {{cite docs/subsystems/llm-streaming.md}} and {{cite docs/subsystems/system-prompt.md}}.

Many APIs send a system prompt as one field on each request. {{project name}} instead keeps it in the durable session history. Thus a reader of the session log can see the system prompt that the model got ({{cite docs/architecture.md:112}}).

By default, the loop appends a new system/message event that replaces the first system node in the model-visible history. It also clears later system nodes ({{cite packages/core/agent-loop/src/runtime-context.ts:100-104}}, {{cite packages/core/agent-loop/src/runtime-context.ts:110-114}}). The other route applies only when the prepared call has systemPromptUpdate: 'in-history'. Then the loop appends each change as a new system node ({{cite packages/core/agent-loop/src/agent.ts:453-454}}, {{cite packages/core/agent-loop/src/runtime-context.ts:106-107}}). Even on that route, the start of a new request series with a changed prompt uses the replace path ({{cite packages/core/agent-loop/src/runtime-context.ts:100}}).

What can go wrong

To change the provider, model or reasoning effort, call agent.model.select() before step preparation. The deprecated agent/request hook throws if its decision is different from the selection that step preparation already fixed ({{cite packages/core/agent-loop/src/agent.ts:635-640}}, {{cite docs/architecture.md:112}}).

This page leaves out dsh-llm-retry's retry policy, image-attachment pricing and resizing, and reasoning-effort validation. It also leaves out what happens when no adapter is registered for a request's provider name.

Why it matters. To make a model call again from the session log, read the system/message events. Do not look for a separate system field.

Which method must every provider adapter implement?

stream(). It is the only abstract method of LlmAdapter. The other methods have a default ({{cite packages/llm/llm/src/index.ts:208}}, {{cite packages/llm/llm/src/index.ts:297-302}}).

 Does the system prompt reach the model as a hidden request field?

No. The loop commits it as a system/message session event. Thus it is logged history, not a field that only the request carries ({{cite packages/core/agent-loop/src/agent.ts:453-461}}, {{cite docs/architecture.md:112}}).

 What happens when two provider adapters try to register the same provider name?

The second registration fails with DUPLICATE_ADAPTER. Registration is all-or-nothing for the adapter's full provider list ({{cite packages/llm/llm/src/index.ts:393-396}}, {{cite packages/llm/llm/src/index.ts:442-443}}).

 Can the deprecated agent/request hook change which provider or model a step calls?

No. preStep() always fixes a selection first, and it throws if there is none ({{cite packages/core/agent-loop/src/agent.ts:288-291}}). agent/request throws if its proposed config has a different provider, model or effort ({{cite packages/core/agent-loop/src/agent.ts:635-640}}). The hook can change only the other request controls ({{cite docs/architecture.md:112}}).
