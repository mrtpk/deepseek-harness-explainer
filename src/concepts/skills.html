A session injects that catalog as a system reminder, and the model loads one full skill body on demand with the skill tool. --- A {{term skill}} is discovered through a ranked provider in {{term context | ctx}}.skills, then loaded on demand by the model-facing skill tool.

The idea

{{term skill | Skills}} are optional, named instruction sets. They are not entries in the {{term session-log | session log}} ({{cite docs/subsystems/skills.md:5}}). ctx.skills is the registry. One or more providers list candidate skills, and the registry merges them into one catalog, by name ({{cite packages/skill/skill/src/index.ts:345-356}}). The shipped local provider scans project and user folders, and each folder kind has a fixed rank ({{cite packages/skill/skill-filesystem/src/index.ts:251-271}}). In one registry layer, a project skill thus wins over a personal skill with the same name ({{cite docs/subsystems/skills.md:15}}).

An everyday comparison. Think of a hotel's binder of house procedures on a shelf, and the shelf's own index card listing every binder's title and one-line summary. A guest reads the index card first, and only pulls one specific binder off the shelf when a task needs it. The comparison stops here. A real index card does not change between visits. A session's skill catalog can change between model steps, because the consumer compares it again before each step ({{cite packages/skill/tool-skill/src/index.ts:217-240}}).

In the code

Step 1: a provider registers with ctx.skills, and scans its roots in rank order

The local filesystem provider registers itself with ctx.skills.registerProvider() ({{cite packages/skill/skill-filesystem/src/index.ts:135-138}}). It scans six kinds of root, and each kind has a fixed rank. In order: project-dsh (100), project-agents (200), zero or more custom folders (300), user-dsh (400), user-agents (500), and an opt-in bundled folder (600) ({{cite packages/skill/skill-filesystem/src/index.ts:35-39}}, {{cite packages/skill/skill/src/index.ts:28}}, {{cite packages/skill/skill-filesystem/src/index.ts:251-271}}). The two project roots need a known working directory ({{cite packages/skill/skill-filesystem/src/index.ts:253}}).

Step 2: a session injects the catalog as a system reminder

Before a model step, dsh-tool-skill reads ctx.skills.snapshot(). It does this only when the agent can see its skill tool ({{cite packages/skill/tool-skill/src/index.ts:224-227}}). It compares the result with the newest catalog that the session still shows. It adds a new catalog message only when the two are different ({{cite packages/skill/tool-skill/src/index.ts:233-254}}). The message is a user message in a <system-reminder> block ({{cite packages/skill/tool-skill/src/index.ts:258-263}}). Only model-invocable skills enter the catalog. Each entry has a name and a shortened description, but not the skill's body ({{cite packages/skill/tool-skill/src/index.ts:229-230}}, {{cite packages/skill/tool-skill/src/index.ts:53-61}}).

Step 3: the model loads one full skill with the skill tool

The skill tool takes one name argument. It finds the name in the current result of ctx.skills.list(), not in the logged catalog message. It refuses the name if the skill does not permit model invocation. Then it calls ctx.skills.get() and returns the full body ({{cite packages/skill/tool-skill/src/index.ts:130-159}}).

More detail

Within one layer, the registry selects a duplicate skill name first by rank, then by provider order ({{cite docs/subsystems/skills.md:15}}). The registry also has layers by scope, the same as ctx.tools. An unscoped registration goes into the global layer. A plugin that one agent preset mounts goes into that preset's own layer. The nearest layer's entry wins a duplicate name, and rank does not apply across layers ({{cite packages/skill/skill/src/index.ts:345-352}}). The project root is the nearest ancestor directory that contains .git. If there is none, the provider uses the given working directory ({{cite packages/skill/skill-filesystem/src/index.ts:959-968}}).

The dsh-tool-skill config field catalogDescriptionMaxLength sets the maximum length of a catalog description. Its default is 500 characters ({{cite packages/skill/tool-skill/src/index.ts:28}}, {{cite packages/skill/tool-skill/src/index.ts:70-72}}). A longer description is cut and ends with ... ({{cite packages/skill/tool-skill/src/index.ts:411-414}}). The registry does not cache a full skill body. Each get() call asks the winning provider again, so the local provider reads the current body ({{cite docs/subsystems/skills.md:192}}).

For the full generated service and type reference, see the repository's own {{cite docs/subsystems/skills.md}}.

A skill's policy has two independent booleans, modelInvocable and userInvocable. In a local skill file, the frontmatter keys are disable-model-invocation and user-invocable. If a key is not there, both booleans are true ({{cite packages/skill/skill-filesystem/src/index.ts:1014-1024}}). The old camelCase keys, for example modelInvocable, are not accepted. The provider ignores that skill file and logs a warning ({{cite packages/skill/skill-filesystem/src/index.ts:1015-1017}}, {{cite packages/skill/skill-filesystem/src/index.ts:838-843}}).

What can go wrong

Check each configured root before you decide that a skill is missing. A root that the provider cannot read gives no candidates. Thus a lower-priority skill with the same name from another root can answer until the failed root recovers ({{cite docs/subsystems/skills.md:77}}, {{cite packages/skill/skill-filesystem/src/index.ts:201-205}}).

This page leaves out remote and embedded skill providers, and the Chokidar file watcher that invalidates the catalog. It also leaves out the session skill catalog that a client can read without a live agent.

Why it matters. If a skill is not in the catalog after an edit, read the log first. The provider logs a warning for a skipped root and for an ignored skill file, for example bad frontmatter ({{cite packages/skill/skill-filesystem/src/index.ts:204}}, {{cite packages/skill/skill-filesystem/src/index.ts:842}}).

What does the skill catalog that reaches the model contain?

Only the name and the shortened description of each model-invocable skill. It does not contain the body ({{cite packages/skill/tool-skill/src/index.ts:229-230}}, {{cite packages/skill/tool-skill/src/index.ts:53-61}}).

 Which root wins when a project skill and a user skill share the same name?

The project skill, if both are in the same registry layer. project-dsh (rank 100) and project-agents (rank 200) both have a lower rank than user-dsh (rank 400) and user-agents (rank 500). A lower rank wins ({{cite packages/skill/skill-filesystem/src/index.ts:35-39}}, {{cite packages/skill/skill/src/index.ts:807-810}}).

 Does the registry cache a skill's full body between calls?

No. Each ctx.skills.get() call asks the provider of the winning candidate again. The local provider then reads the current body ({{cite docs/subsystems/skills.md:192}}).

 A skill file sets disable-model-invocation to true, so its policy is modelInvocable false and userInvocable true. Can the model's skill tool load it?

No. The skill tool checks isModelInvocable two times: on the listed summary and on the loaded definition. It refuses the call if either check is false ({{cite packages/skill/tool-skill/src/index.ts:142-151}}). Only a user's /name can load this skill ({{cite packages/skill/tool-skill/src/index.ts:179-180}}).
