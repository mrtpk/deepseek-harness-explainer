A session injects that catalog as a system reminder, and the model loads one full skill body on demand with the skill tool. --- A {{term skill}} is discovered through a ranked provider in {{term context | ctx}}.skills, then loaded on demand by the model-facing skill tool.

The idea

{{term skill | Skills}} are optional, named instruction sets. They are not entries in the {{term session-log | session log}} ({{cite docs/subsystems/skills.md:5}}). ctx.skills is the registry: one or more providers list candidate skills, and the registry merges them into one catalog, by name ({{cite packages/skill/skill/src/index.ts:356}}). The shipped local provider scans a fixed set of project and user folders, in a fixed rank order. A project's own skill can therefore always win over a personal one with the same name ({{cite packages/skill/skill-filesystem/src/index.ts:256-268}}).

An everyday comparison. Think of a hotel's binder of house procedures on a shelf, and the shelf's own index card listing every binder's title and one-line summary. A guest reads the index card first, and only pulls one specific binder off the shelf when a task needs it. The comparison stops here. A real index card does not change between visits; a session's skill catalog can, because discovery re-scans the roots.

In the code

Step 1: a provider registers with ctx.skills, and scans its roots in rank order

The local filesystem provider registers itself with ctx.skills.registerProvider() ({{cite packages/skill/skill-filesystem/src/index.ts:135}}). It scans six possible roots, each with a fixed rank. In order: project-dsh (100), project-agents (200), custom (300), user-dsh (400), user-agents (500), and an opt-in bundled root (600) ({{cite packages/skill/skill-filesystem/src/index.ts:35-39}}, {{cite packages/skill/skill-filesystem/src/index.ts:256-268}}).

Step 2: a session injects the catalog as a system reminder

Before a model step, dsh-tool-skill reads ctx.skills.snapshot() and compares it with the newest catalog message already in the session ({{cite packages/skill/tool-skill/src/index.ts:217-232}}). Only model-invocable skills, by name and description, enter that catalog; it never carries a skill's body ({{cite packages/skill/tool-skill/src/index.ts:229-230}}).

Step 3: the model loads one full skill with the skill tool

The skill tool takes one name argument. It looks the name up in the current catalog, then rejects it unless the skill permits model invocation. It then calls ctx.skills.get() to load and return the full body ({{cite packages/skill/tool-skill/src/index.ts:130-151}}).

More detail

Within one layer, a duplicate skill name resolves first by rank, then by provider order ({{cite docs/subsystems/skills.md:15}}). The registry is also layered by scope, the same way ctx.tools is. An unscoped registration lands in the global layer. A plugin mounted by one agent preset lands in that preset's own layer instead. A scoped entry wins over a global one with the same name, regardless of rank ({{cite docs/subsystems/skills.md:13}}). The project root is the nearest ancestor directory containing .git; without one, it falls back to the given working directory ({{cite packages/skill/skill-filesystem/src/index.ts:959-968}}).

One config knob changes how long a catalog description can be: catalogDescriptionMaxLength, a constant defaulting to 500 characters, applied through the consumer's own config schema ({{cite packages/skill/tool-skill/src/index.ts:28}}, {{cite packages/skill/tool-skill/src/index.ts:71}}). The registry never caches a full skill body. Every get() call re-reads it from the winning provider, so a body-only edit is visible on the very next load ({{cite docs/subsystems/skills.md:192}}).

For the full generated service and type reference, see the repository's own {{cite docs/subsystems/skills.md}}.

A skill's frontmatter sets two independent booleans, not one. Both default to true when the key is left out ({{cite docs/subsystems/skills.md:128}}).

modelInvocableuserInvocableMeaning
truetrueThe default: the model can call it, and a user can type /name to invoke it.
truefalseModel-only: it never appears in a user-facing command catalog.
falsetrueUser-only: the skill tool refuses to load it for the model.
falsefalseHidden from both catalogs; only a trusted caller of ctx.skills.get() can still load it.

What can go wrong

Check every configured root before you assume a skill is missing. A root that fails to read contributes no candidates, so a lower-priority, same-named skill from another root may answer instead, until the failed root recovers ({{cite docs/subsystems/skills.md:77}}).

This page leaves out remote and embedded skill providers, and the Chokidar file watcher that invalidates the catalog. It also leaves out the browser-facing session skill catalog used without a live agent.

Why it matters. A skill that "disappeared" after an edit is more often a provider read failure than a deleted file; re-run discovery before you rewrite the skill.

What does the skill catalog that reaches the model contain?

Only each model-invocable skill's name and description, never its body ({{cite packages/skill/tool-skill/src/index.ts:229-230}}).

 Which root wins when a project skill and a user skill share the same name?

The project skill. project-dsh (rank 100) and project-agents (rank 200) both outrank user-dsh (rank 400) and user-agents (rank 500) ({{cite packages/skill/skill-filesystem/src/index.ts:35-39}}).

 Does the registry cache a skill's full body between calls?

No. Each ctx.skills.get() call re-reads the winning candidate from its provider, so a body-only edit changes the very next load ({{cite docs/subsystems/skills.md:192}}).

 A skill sets modelInvocable to false and userInvocable to true. Can the model's skill tool load it?

No. The skill tool checks isModelInvocable twice: once on the catalog summary, once on the loaded definition. It refuses the call either time the check is false ({{cite packages/skill/tool-skill/src/index.ts:142-151}}).
