Each shipped profile mounts the seam for its surface. --- A client reaches dsh through the ACP server, the SDK wire protocol, or the Web and Desktop connection layer.

The idea

dsh has three separate protocol seams for three kinds of client. The {{term acp | ACP}} server speaks a standard, automation-only JSON-RPC protocol over stdio. It intentionally leaves out DSH-specific presentation data and interactive UI features ({{cite packages/acp/acp/README.md:2}}, {{cite packages/acp/acp/README.md:12}}). The {{term sdk-wire-protocol | SDK wire protocol}} is dsh's own newline-delimited JSON-RPC. dsh-sdk-jsonrpc-server serves it over stdio, and the TypeScript and Python SDKs speak it ({{cite packages/sdk/protocol/README.md:12}}, {{cite packages/sdk/server/README.md:12}}). Web and Desktop speak Remote RPC. The browser uses HTTP POST for unary calls, and a Gateway-owned WebSocket carries the streams ({{cite packages/client/connection/README.md:12}}, {{cite packages/client/connection/README.md:34}}).

An everyday comparison. Think of a building with three doors: a loading dock for scripted deliveries, a maintenance door for automation, and the main lobby for people. The comparison stops here. In dsh, the {{term profile}} decides which doors a deployment opens.

The picture

Read panel 1 as three independent doors into the same session and agent-loop core. Each door is its own plugin. Read panel 2 as a special case of the SDK seam. The Python SDK adds no protocol of its own.

In the code

Step 1: the ACP server exposes a fixed set of session methods

initialize() reports one protocol version. It also reports the session capabilities that this server adds to the ACP v1 baseline: close, list and resume ({{cite packages/acp/acp/src/index.ts:179-193}}). One connection can run several independent sessions at the same time ({{cite packages/acp/acp/README.md:60}}).

Step 2: the SDK wire protocol is one JSON-RPC message per line

Both wire ends of the SDK protocol use one rule: one JSON-RPC 2.0 message per newline-terminated line over a byte stream ({{cite packages/sdk/protocol/README.md:34}}). The TypeScript client finds the same-version @deepseek-ai/dsh executable, unless the caller gives one in dshBin. The client owns that subprocess and reaps it on close() ({{cite packages/sdk/client/README.md:12}}).

Step 3: the Python SDK launches the same binary; it has no protocol of its own

The Python SDK drives DeepSeek Harness as a subprocess, over the same newline-delimited JSON-RPC on stdio ({{cite python/README.md:5}}). It has no separate application entrypoint. It launches the bundled dsh CLI with --profile sdk. That profile owns the JSON-RPC server, agent composition, and persistence ({{cite python/sdk/README.md:31}}).

Step 4: Web and Desktop share one connection carrier

The browser sends Remote RPC calls over HTTP POST. A Gateway-owned WebSocket carries the streams ({{cite packages/client/connection/README.md:34}}). Desktop uses the same connection package. Its page gets the HTTP origin of its own Host as streamBaseUrl. The Gateway uses that origin for its WebSocket ({{cite packages/client/connection/README.md:30}}, {{cite apps/desktop/src/main.ts:790}}).

More detail

A different bundle mounts each seam. The acp-app bundle mounts dsh-acp ({{cite packages/bundle/acp-app/cordis.patch.yml:15-16}}). The sdk-app and sdk-minimal bundles mount dsh-sdk-jsonrpc-server ({{cite packages/bundle/sdk-app/cordis.patch.yml:17-18}}, {{cite packages/bundle/sdk-minimal/cordis.patch.yml:11-12}}). The web-app bundle mounts dsh-client-connection ({{cite packages/bundle/web-app/cordis.patch.yml:230-231}}). The sdk-app bundle also mounts the connection package, but it starts no Web server ({{cite packages/bundle/sdk-app/cordis.patch.yml:46-49}}). {{link learn/profiles-and-bundles | The profiles page}} tells how a profile assembles its plugin tree.

ACP and the SDK server each register an answerer on the approval waterfall that {{link concepts/approval-and-interaction | the approval page}} describes. The ACP answerer handles each ask for its own agents that has a tool-call id ({{cite packages/acp/acp/src/index.ts:158-160}}). The SDK answerer works only when the client sets approvalRequests in initialize ({{cite packages/sdk/server/src/server.ts:130-131}}, {{cite packages/sdk/server/src/server.ts:258}}).

The two automation protocols set the model route differently. ACP's provider and model are plugin config. They are the start route of each session that the server makes ({{cite packages/acp/acp/README.md:47-48}}). An ACP client can then change the model or reasoning_effort of one session with session/set_config_option ({{cite packages/acp/acp/README.md:70}}, {{cite packages/acp/acp/src/model-control.ts:30-34}}). The SDK sets its route for each connection, in the initialize handshake, with an optional reasoningEffort and maxTokens ({{cite packages/sdk/client/README.md:79}}).

No single generated subsystems page covers all three seams. The package READMEs cited above are the deeper reference. The repository's own {{cite docs/subsystems/web-client.md}} covers the Web Client architecture.

What can go wrong

The TypeScript client finds the same-version @deepseek-ai/dsh executable, unless dshBin names one ({{cite packages/sdk/client/README.md:12}}). start() runs a bounded initialize handshake. The server checks the route before it accepts prompts. The default handshake timeout is 10 seconds, and the error names the profile and the stderr tail ({{cite packages/sdk/client/README.md:79}}).

This page leaves out MCP server mounting, session persistence and resume, image-prompt support, and the exact Remote RPC attachment format.

Why it matters. No SDK runs the harness inside the caller's process. The TypeScript client and the Python SDK each start a dsh subprocess ({{cite packages/sdk/client/README.md:12}}, {{cite python/sdk/README.md:31}}). Thus each client instance talks to its own runtime process.

Which of the three protocol seams is automation-only and intentionally leaves out DSH-specific presentation data?

The ACP server. It exposes only the standard ACP v1 surface ({{cite packages/acp/acp/README.md:12}}, {{cite packages/acp/acp/README.md:32}}).

 Does the Python SDK define its own wire protocol?

No. It launches the bundled dsh --profile sdk binary. It speaks the same newline-delimited JSON-RPC-on-stdio protocol that the SDK server serves ({{cite python/README.md:5}}, {{cite python/sdk/README.md:31}}).

 How does the Desktop app's page reach its own local Host, and not a remote Web deployment?

The Desktop main process gives the page the origin of its own Host as streamBaseUrl. The Gateway uses that origin for its WebSocket. The HTTP transport is selected separately ({{cite packages/client/connection/README.md:30}}, {{cite apps/desktop/src/main.ts:790}}).

 An ACP deployment sets provider and model in plugin config. Can an ACP client run one session on a different model?

Yes. The config gives the start route of each new session ({{cite packages/acp/acp/README.md:47-48}}). A client can then send session/set_config_option with the advertised model option. The change applies from that agent's next model step ({{cite packages/acp/acp/README.md:70}}, {{cite packages/acp/acp/src/model-control.ts:30-34}}). In the SDK, the client sets the route in its initialize handshake ({{cite packages/sdk/client/README.md:79}}).
