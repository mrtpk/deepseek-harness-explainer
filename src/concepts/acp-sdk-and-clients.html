The idea

dsh exposes three separate protocol seams for three kinds of client. The {{term acp | ACP}} server is a generic, automation-only JSON-RPC-over-stdio protocol; it deliberately leaves out DSH-specific presentation data so any ACP-speaking client can drive it ({{cite packages/acp/acp/README.md:11}}). The {{term sdk-wire-protocol | SDK wire protocol}} is dsh's own newline-delimited JSON-RPC, served over stdio by dsh-sdk-jsonrpc-server and spoken by the TypeScript and Python SDKs ({{cite packages/sdk/protocol/README.md:12}}). Web and Desktop instead speak Remote RPC: JSON over HTTP POST for one-off calls, plus one WebSocket event stream ({{cite packages/client/connection/README.md:12}}, {{cite packages/client/connection/README.md:34}}).

An everyday comparison. Think of a building with three doors: a loading dock for scripted deliveries, a maintenance door for certified automation, and the main lobby for people. The comparison stops here. A single dsh deployment normally opens only one of these doors at a time, chosen by its {{term profile}}.

The picture

Read panel 1 as three independent doors, each its own plugin, into the same session and agent-loop core covered on earlier pages. Read panel 2 as a special case of the SDK seam: the Python SDK adds no protocol of its own.

In the code

Step 1: the ACP server exposes a fixed set of session methods

initialize() reports one protocol version plus the session methods this server adds beyond the ACP v1 baseline, such as session/list and session/resume ({{cite packages/acp/acp/src/index.ts:179-193}}). One connection can run several independent sessions at once.

Step 2: the SDK wire protocol is one JSON-RPC message per line

Both wire ends of the SDK protocol agree on one rule: one JSON-RPC 2.0 message per newline-terminated line over a byte stream ({{cite packages/sdk/protocol/README.md:34}}). The TypeScript client resolves the matching @deepseek-ai/dsh executable unless the caller names one explicitly. It then owns that subprocess for the life of the client ({{cite packages/sdk/client/README.md:12}}).

Step 3: the Python SDK launches the same binary; it has no protocol of its own

The Python SDK drives DeepSeek Harness as a subprocess, over the same newline-delimited JSON-RPC on stdio, with no in-process harness logic of its own ({{cite python/README.md:5}}). It has no separate application entrypoint: it launches the bundled dsh CLI with --profile sdk, and that profile owns the JSON-RPC server, agent composition, and persistence ({{cite python/sdk/README.md:31}}).

Step 4: Web and Desktop share one connection carrier

The browser issues Remote RPC calls over HTTP POST; a Gateway-owned WebSocket carries the matching event stream ({{cite packages/client/connection/README.md:34}}). Desktop reuses the exact same carrier. It supplies its own HTTP origin as streamBaseUrl for a locally hosted runtime, instead of a browser's page origin ({{cite packages/client/connection/README.md:30}}, {{cite apps/desktop/src/main.ts:790}}).

More detail

Each seam is mounted by a different profile. The shipped acp profile mounts dsh-acp; the sdk and sdk-minimal profiles mount dsh-sdk-jsonrpc-server; the web profile mounts the connection and UI plugins. {{link learn/profiles-and-bundles | The profiles page}} covers how a profile assembles its plugin tree; this page only names which plugin backs each surface. Both ACP and the SDK server also register their own opt-in approval answerer, on the same waterfall described on {{link concepts/approval-and-interaction | the approval page}}.

The two automation protocols configure the model route differently. ACP's provider and model are plugin config, so they apply to every session the server creates ({{cite packages/acp/acp/README.md:47-48}}). The SDK sets its route per connection, inside the initialize handshake, together with an optional reasoningEffort and maxTokens ({{cite packages/sdk/client/README.md:79}}).

No single generated subsystems page covers all three seams; the package READMEs cited above are the deeper reference. The repository's own {{cite docs/subsystems/web-client.md}} covers the Web Client's own architecture.

What can go wrong

The TypeScript client resolves the same-version @deepseek-ai/dsh executable unless dshBin names one explicitly. A mismatched or missing binary surfaces as a bounded initialize handshake failure, not as a protocol error later in the run ({{cite packages/sdk/client/README.md:12}}, {{cite packages/sdk/client/README.md:79}}).

This page leaves out MCP server mounting, session persistence and resume, image-prompt support, and the exact Remote RPC attachment format.

Why it matters. A caller might assume the Node and Python SDKs share one process model. They do not: the Python SDK spawns and owns its own dsh subprocess. Two Python SDK instances mean two separate runtimes, each with its own Harness home.

Which of the three protocol seams is automation-only and intentionally leaves out DSH-specific presentation data?

The ACP server: it exposes only the standard ACP v1 surface plus a small set of session extensions ({{cite packages/acp/acp/README.md:11}}).

 Does the Python SDK define its own wire protocol?

No. It launches the bundled dsh --profile sdk binary and speaks the same newline-delimited JSON-RPC-on-stdio protocol the SDK server already serves, with no in-process harness logic ({{cite python/README.md:5}}, {{cite python/sdk/README.md:31}}).

 How does the Desktop app's browser view reach its own locally hosted runtime, rather than a remote Web deployment?

It supplies its own HTTP origin as streamBaseUrl to the same browser connection carrier. The Gateway then uses that origin for its WebSocket; HTTP transport is selected independently ({{cite packages/client/connection/README.md:30}}, {{cite apps/desktop/src/main.ts:790}}).

 A deployment wants every session to use the same fixed model, with no per-connection override. Should it choose the ACP server or the SDK server?

The ACP server: its provider and model are plugin config applied to every session it creates. The SDK server instead takes the route per connection, inside each client's own initialize handshake ({{cite packages/acp/acp/README.md:47-48}}, {{cite packages/sdk/client/README.md:79}}).
