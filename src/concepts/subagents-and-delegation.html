Local providers keep a durable child session; others run once. --- A parent agent delegates a task to a child through a named {{term subagent-provider | provider}} registered on {{term subagent | ctx.subagents}}.

The idea

ctx.subagents does not run children itself. It is a named-provider registry: each backend registers under a unique name, and a parent picks one by name when it starts a child ({{cite packages/subagent/subagent/src/index.ts:194}}, {{cite packages/subagent/subagent/src/index.ts:549-568}}). One shared SubagentManager then owns every accepted child's lifecycle, no matter which provider started it ({{cite packages/subagent/subagent/README.md:12}}).

An everyday comparison. Think of a dispatcher who hands a job to one of several outside contractors by name. Some contractors stay on call and take a follow-up job later; others do the one job and close the file. The comparison stops here. The dispatcher also fixes what each contractor may touch before the job starts, and that scope never widens later, even if the contractor asks.

In the code

Step 1: startActivation() resolves the named provider, then checks its capabilities

startActivation() looks up the provider, rejects any requested capability the provider does not declare, then hands off to the manager's local or external start path ({{cite packages/subagent/subagent/src/index.ts:271-286}}).

Step 2: method presence on the provider decides local or external

A provider that implements prepareContinuable() seeds a local, resumable child {{term session}}. One that implements only start() returns a single execution handle and accepts no later message ({{cite packages/subagent/subagent/src/types.ts:313-356}}). The in-process spawn and fork providers both implement prepareContinuable() ({{cite packages/subagent/subagent-spawn-in-process/src/index.ts:50}}, {{cite packages/subagent/subagent-fork-in-process/src/index.ts:72}}). The claude-code, codex, acp and dsh-sdk providers each implement only start() ({{cite packages/subagent/subagent-claude-code/src/index.ts:73-116}}).

Step 3: the Claude Code provider runs the official SDK, not the host's own CLI

dsh ships a Claude Code subagent provider. Each run calls the official Claude Agent SDK's query() and supplies a custom spawn callback. This callback hands the SDK's own real Claude Code CLI process to dsh's shared subprocess owner, instead of letting it run untracked ({{cite packages/subagent/subagent-claude-code/src/index.ts:100-114}}).

The provider never falls back to a claude executable already on the host; the SDK starts its own platform-pinned runtime on demand ({{cite packages/subagent/subagent-claude-code/README.md:12}}).

Step 4: tool restriction for a delegated scope

A {{term tool-restriction | tool restriction}} is an allow/deny name list applied with ctx.tools.restrict() on the child's own scope ({{cite packages/core/tools/src/contracts.ts:376-381}}, {{cite packages/core/tools/src/index.ts:162-189}}). The subagent package still carries this call for one case: replaying a historical toolFilter recorded on an older child's descriptor when that child cold-resumes ({{cite packages/subagent/subagent/src/child-agent.ts:217}}, {{cite packages/subagent/subagent/src/manager.ts:1395}}). For a new child, the delegation tool's own persona and toolFilter config fields are no longer accepted. Tool and persona selection now goes through an Agent Preset chosen with agentPreset ({{cite packages/subagent/tool-subagent/src/index.ts:151-154}}).

More detail

Two numeric limits apply before any child starts. Delegation depth defaults to 1 and is resolved per call by resolveMaxDepth(), which returns undefined (no host-enforced cap) only when the tool sets 'provider-managed' ({{cite packages/subagent/subagent/src/index.ts:196}}, {{cite packages/subagent/subagent/src/index.ts:244-250}}). A child's own depth is the parent's persisted depth plus one. The code reads this from the session header, not from runtime options, so a resumed child cannot delegate as if it were top-level ({{cite packages/subagent/subagent/src/child-agent.ts:49-58}}). Separately, maxActiveSubagents caps live and materializing children in one activation tree at 8 by default ({{cite packages/subagent/subagent/src/index.ts:197}}).

A delegated child's permission scope is fixed at the moment it starts. The manager captures the parent's sandbox-mode override and current permission preset synchronously, before the child's first await. It always pins the child's own approval policy to 'never', regardless of the parent's policy ({{cite packages/subagent/subagent/src/child-agent.ts:248-255}}). It then appends these as the child's own first session events, so the child's effective policy can be read back from its own log ({{cite packages/subagent/subagent/src/child-agent.ts:266-279}}). Every in-process child also carries one fixed delegation-scope sentence in its runtime context, telling it that this scope cannot widen from inside the session ({{cite packages/subagent/subagent/src/child-agent.ts:171-175}}).

For the full generated service and event reference, see the repository's own {{cite docs/subsystems/subagent.md}}.

What can go wrong

A dsh-tool-subagent configuration that still sets persona or toolFilter directly fails at plugin load. Configure tools and persona in an Agent Preset and select it with agentPreset instead ({{cite packages/subagent/tool-subagent/src/index.ts:151-154}}).

This page leaves out child discovery and catalogs, sendMessage() adjacency rules, interrupting a running child, and the ACP, Codex and DSH SDK provider transports.

Why it matters. The README's package-level claims do not say whether an old toolFilter setting still works. The config field itself is rejected at load. Only the replay machinery for already-created children remains.

Which two providers in this codebase give a child a durable, resumable session?

spawn and fork, the only providers that implement prepareContinuable() ({{cite packages/subagent/subagent-spawn-in-process/src/index.ts:50}}, {{cite packages/subagent/subagent-fork-in-process/src/index.ts:72}}).

 Does the Claude Code subagent provider run the host machine's own installed claude command?

No. It calls the official Claude Agent SDK's query(), which starts its own platform-pinned CLI process under dsh's subprocess owner. It never falls back to a host executable ({{cite packages/subagent/subagent-claude-code/README.md:12}}, {{cite packages/subagent/subagent-claude-code/src/index.ts:100-114}}).

 A tool configures maxDepth: 'provider-managed'. What does resolveMaxDepth() return?

undefined: no host-enforced numeric cap. The provider's own runtime owns the recursion budget instead ({{cite packages/subagent/subagent/src/index.ts:244-246}}).

 A request sets outputSchema, but the named provider's capabilities.outputSchema is false. What happens?

startActivation() throws UNSUPPORTED_CAPABILITY before any child starts: assertCapabilities() rejects the first requested field the provider does not declare support for ({{cite packages/subagent/subagent/src/index.ts:632-653}}, {{cite packages/subagent/subagent/src/types.ts:127}}).
