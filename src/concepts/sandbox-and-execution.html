Shell and terminal wrap the subprocess; fs checks the path itself. --- ctx.sandboxPolicy resolves one file-effect mode for each call, and two of three capability families enforce it by wrapping a subprocess.

The idea

A {{term capability-seam | capability seam}} swaps in different code for the same job. The {{term sandbox | sandbox}} seam is the file-effect version. It wraps a subprocess under one of three modes: read-only, workspace-write, or danger-full-access ({{cite packages/sandbox/sandbox/src/index.ts:30}}). The mode governs files only; network access and process visibility sit outside this vocabulary ({{cite packages/sandbox/sandbox/src/index.ts:27-28}}). One service, ctx.sandboxPolicy, resolves which mode and which workspace root apply to one call; a second service, ctx.sandbox, does the actual wrapping.

An everyday comparison. Think of a hotel key card that opens some doors and not others, reissued fresh for every guest. The comparison stops here. A key card stays fixed for a stay. A denied dsh call can ask for a wider card for one retry only, through a human approval ({{link concepts/approval-and-interaction | the approval page}}).

The picture

Read panel 1 top to bottom: an approved escalation outranks the session's own override, which outranks the deployment default. Read panel 2 as two answers to one question: how is a mode enforced? Wrapping a process is a kernel boundary; checking a path is not.

In the code

Step 1: ctx.sandboxPolicy.resolve() picks one mode and one root

resolve() merges three sources in order: a caller-approved mode override first, then the session's last sandbox/mode event, then the deployment default ({{cite packages/sandbox/sandbox-policy/src/index.ts:197-205}}). The deployment default comes from plugin config and defaults to read-only in the schema, then lands on the service in its constructor ({{cite packages/sandbox/sandbox-policy/src/index.ts:136-142}}, {{cite packages/sandbox/sandbox-policy/src/index.ts:159}}). The workspace root is the calling session's own current directory; the configured workspaceRoot covers only calls without a session cwd ({{cite packages/sandbox/sandbox-policy/src/index.ts:200-201}}).

Step 2: shell and terminal wrap the subprocess argv

The bash and terminal executors both hand their argv to ctx.sandbox.confine(argv, policy) and spawn whatever argv it returns instead ({{cite packages/shell/bash-sandbox/src/index.ts:187-189}}, {{cite packages/terminal/terminal-bash/src/index.ts:97-106}}). Only a confined mode reaches ctx.sandbox; under danger-full-access the executor spawns the caller's own argv unchanged ({{cite packages/shell/bash-sandbox/src/index.ts:92-97}}).

Step 3: fs checks the path itself, with no ctx.sandbox call

The filesystem backend never calls ctx.sandbox. It canonicalizes the target path and checks it lands under a writable root, in the same trusted process. This is a policy check in trusted code over a model-controlled path, not a kernel boundary ({{cite packages/fs/fs-sandbox/src/index.ts:10-14}}). read-only denies every mutation outright; workspace-write requires containment under the resolved root ({{cite packages/fs/fs-sandbox/src/index.ts:156-178}}).

More detail

A denial is not always final. A tool may retry the exact same call as a {{term sandbox-escalation | sandbox escalation}}: a sandbox_permissions argument names a strictly wider mode, plus a justification. approveEscalation() checks the target is actually wider, then routes the request through ctx.approval before anything executes ({{cite packages/sandbox/sandbox/src/escalation.ts:172-206}}). The grant applies to that one call only. {{link concepts/approval-and-interaction | The approval page}} covers how that one decision gets made; this page covers only the sandbox-mode side of the handshake.

Enforcement is a reported fact, not a guarantee from the mode name alone. A backend reports full when it governs every file effect its mode promises. It reports partial when an older kernel ABI or a less complete backend covers only some of them ({{cite packages/sandbox/sandbox/src/index.ts:62-67}}). A caller that needs an absolute boundary must check this fact and must not treat partial as full. When no backend can enforce a confined mode at all, ctx.sandbox.confine() fails closed with SandboxUnavailableError instead of running the command unconfined ({{cite packages/sandbox/sandbox/src/index.ts:139-152}}).

For the full generated service and type reference, see the repository's own {{cite docs/subsystems/sandbox.md}}.

What can go wrong

A read-only or workspace-write mode confines file effects only. A confined subprocess can still reach the network or see other processes, unless some other capability restricts that separately ({{cite packages/sandbox/sandbox/src/index.ts:27-28}}).

This page leaves out the bwrap, Landlock, Seatbelt, and Windows ACL runner dialects, and the SSH sandbox backend. It also leaves out the delegated-child sandbox override covered on {{link concepts/subagents-and-delegation}}.

Why it matters. A reader who only learns the three mode names could assume workspace-write also blocks outbound network calls. It does not. A sandboxed shell command can still reach the network even while every write it attempts outside the workspace is denied.

What are the three sandbox modes, and which one skips ctx.sandbox entirely?

read-only, workspace-write, and danger-full-access ({{cite packages/sandbox/sandbox/src/index.ts:30}}). Only the first two are confined modes; a danger-full-access call spawns its own argv unchanged and never reaches ctx.sandbox ({{cite packages/shell/bash-sandbox/src/index.ts:92-97}}).

 Which capability family does not call ctx.sandbox.confine() to enforce its policy, and what does it do instead?

fs. It canonicalizes the target path and checks containment under a writable root itself, in trusted code, with no kernel-level wrap ({{cite packages/fs/fs-sandbox/src/index.ts:156-178}}).

 A session has logged a sandbox/mode override, and the deployment also configures a default mode. Which one does resolve() use?

The session's own override. An explicit per-call approved mode outranks it, but the session override always outranks the deployment default ({{cite packages/sandbox/sandbox-policy/src/index.ts:200}}).

 A call's effective mode is workspace-write. Can it escalate to read-only to loosen its own restriction?

No. read-only is narrower than workspace-write, not wider, so it is not a valid escalation target; only danger-full-access is strictly wider than workspace-write ({{cite packages/sandbox/sandbox/src/escalation.ts:29-32}}).
