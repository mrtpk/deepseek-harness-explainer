Two of three capability families enforce it when they wrap a subprocess.

The idea

A {{term capability-seam | capability seam}} swaps in different code for the same job. The {{term sandbox | sandbox}} seam is the file-effect version. It wraps a subprocess under one of three modes: read-only, workspace-write, or danger-full-access ({{cite packages/sandbox/sandbox/src/index.ts:30}}). The mode controls file effects only. Network access and process visibility are outside this vocabulary ({{cite packages/sandbox/sandbox/src/index.ts:24-28}}). One service, ctx.sandboxPolicy, resolves the mode and the workspace root for one call ({{cite packages/sandbox/sandbox-policy/src/index.ts:128-133}}). A second service, ctx.sandbox, wraps the subprocess ({{cite packages/shell/bash-sandbox/src/index.ts:187-189}}).

An everyday comparison. Think of a hotel key card that opens some doors and not others. The hotel makes a new card for each guest. The comparison stops here. A key card stays the same for the full stay. A denied dsh call can ask for a wider card for one retry only, through an approval ({{link concepts/approval-and-interaction | the approval page}}).

The picture

In the code

Step 1: ctx.sandboxPolicy.resolve() picks one mode and one root

resolve() uses three sources in order. First is a caller-approved mode override. Next is the session's last sandbox/mode event. Last is the deployment default ({{cite packages/sandbox/sandbox-policy/src/index.ts:197-205}}). The deployment default comes from the plugin config mode ({{cite packages/sandbox/sandbox-policy/src/index.ts:159}}). The schema default is read-only ({{cite packages/sandbox/sandbox-policy/src/index.ts:137}}). But the base bundle sets DSH_PERMISSION_MODE, or else workspace-write ({{cite packages/bundle/base/cordis.patch.yml:243-247}}). The sdk-minimal bundle sets danger-full-access ({{cite packages/bundle/sdk-minimal/cordis.patch.yml:70-74}}). The workspace root is the cwd in the session header. The configured workspaceRoot applies only to calls without a session cwd ({{cite packages/sandbox/sandbox-policy/src/index.ts:201}}).

Step 2: shell and terminal wrap the subprocess argv

The bash and terminal executors both give their argv to ctx.sandbox.confine(argv, policy). Then they spawn the argv that it returns ({{cite packages/shell/bash-sandbox/src/index.ts:98-103}}, {{cite packages/shell/bash-sandbox/src/index.ts:187-189}}, {{cite packages/terminal/terminal-bash/src/index.ts:97-106}}). Only a confined mode reaches ctx.sandbox. Under danger-full-access, the executor spawns the caller's own argv unchanged ({{cite packages/shell/bash-sandbox/src/index.ts:92-97}}, {{cite packages/terminal/terminal-bash/src/index.ts:99}}).

Step 3: fs checks the path itself, with no ctx.sandbox call

The sandboxed filesystem backend does not call ctx.sandbox. It canonicalizes the target path and checks that the path is under a writable root, in the same trusted process. This is a policy check in trusted code over a model-controlled path, not a kernel boundary ({{cite packages/fs/fs-sandbox/src/index.ts:10-14}}). The check applies to mutations only. Reads pass through in all modes ({{cite packages/fs/fs-sandbox/src/index.ts:6-8}}). read-only denies each mutation. workspace-write needs containment under the workspace root, an additional writable root, or a platform temp area ({{cite packages/fs/fs-sandbox/src/index.ts:20-23}}, {{cite packages/fs/fs-sandbox/src/index.ts:156-178}}).

More detail

A denial is not always final. The model can retry the same call as a {{term sandbox-escalation | sandbox escalation}}. The retry adds a sandbox_permissions argument with a strictly wider mode, and a justification ({{cite packages/sandbox/sandbox/src/escalation.ts:44-62}}, {{cite packages/sandbox/sandbox/src/escalation.ts:85-87}}). approveEscalation() checks that the target is wider. Then it sends the request through ctx.approval before the call runs ({{cite packages/sandbox/sandbox/src/escalation.ts:172-206}}). The grant applies to that one call only ({{cite packages/sandbox/sandbox/src/escalation.ts:162-170}}). {{link concepts/approval-and-interaction | The approval page}} tells how the service makes that decision. This page covers only the sandbox side.

The backend reports the enforcement level. The mode name alone does not guarantee it. full means that the backend controls each file effect that the mode promises. partial means that an active backend or an older kernel ABI cannot control all of them ({{cite packages/sandbox/sandbox/src/index.ts:62-67}}). A caller that needs an absolute boundary must not treat partial as full. When no backend can enforce a confined mode, ctx.sandbox.confine() fails closed with SandboxUnavailableError. It does not run the command unconfined ({{cite packages/sandbox/sandbox/src/index.ts:134-152}}).

For the full generated service and type reference, see the repository's own {{cite docs/subsystems/sandbox.md}}.

A call can escalate only to a mode that is strictly wider than its own effective mode ({{cite packages/sandbox/sandbox/src/escalation.ts:29-32}}, {{cite packages/sandbox/sandbox/src/escalation.ts:178-180}}). A request for the current effective mode needs no approval ({{cite packages/sandbox/sandbox/src/escalation.ts:174}}).

What can go wrong

A read-only or workspace-write mode controls file effects only ({{cite packages/sandbox/sandbox/src/index.ts:27-28}}). The bwrap and Seatbelt profiles do not block the network ({{cite packages/sandbox/sandbox-local/src/profiles.ts:16-17}}, {{cite packages/sandbox/sandbox-local/src/profiles.ts:52-53}}). The Windows ACL runner does not limit the network or process visibility ({{cite packages/sandbox/sandbox-windows-acl/src/index.ts:26-28}}). The bwrap profile hides other processes with --unshare-pid, but the mode itself does not promise this.

This page leaves out the bwrap, Landlock, Seatbelt, and Windows ACL runner dialects, and the SSH sandbox backend. It also leaves out the delegated-child sandbox override covered on {{link concepts/subagents-and-delegation}}.

Why it matters. A reader who knows only the three mode names can think that workspace-write also blocks outbound network calls. It does not. Under the bwrap or Seatbelt profile, a sandboxed shell command can reach the network, while the sandbox denies its writes outside the writable roots.

What are the three sandbox modes, and which one skips ctx.sandbox entirely?

read-only, workspace-write, and danger-full-access ({{cite packages/sandbox/sandbox/src/index.ts:30}}). Only the first two are confined modes. A danger-full-access call spawns its own argv unchanged and does not reach ctx.sandbox ({{cite packages/shell/bash-sandbox/src/index.ts:92-97}}, {{cite docs/subsystems/sandbox.md:23}}).

 Which capability family does not call ctx.sandbox.confine() to enforce its policy, and what does it do instead?

fs. It canonicalizes the target path and checks containment under a writable root itself, in trusted code. It does not wrap a process ({{cite packages/fs/fs-sandbox/src/index.ts:156-178}}).

 A session has logged a sandbox/mode override, and the deployment also configures a default mode. Which one does resolve() use?

The session's own override. An explicit approved mode for the call outranks it. The session override outranks the deployment default ({{cite packages/sandbox/sandbox-policy/src/index.ts:200}}).

 A call's effective mode is workspace-write. Can it escalate to read-only?

No. read-only is narrower than workspace-write, so it is not a valid escalation target. approveEscalation() throws before the call runs. Only danger-full-access is strictly wider than workspace-write ({{cite packages/sandbox/sandbox/src/escalation.ts:29-32}}, {{cite packages/sandbox/sandbox/src/escalation.ts:178-180}}).
